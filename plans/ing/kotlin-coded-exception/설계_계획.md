# Kotlin 스켈레톤 예외 구조 정리 — 설계 계획

- 작성일: 2026-10-26
- 근거와 결정 이유: [`리뷰_이력.md`](리뷰_이력.md)

## 1. 목적

Kotlin 스켈레톤 3종에서 HTTP 상태와 구분 코드를 정하는 곳을 `ErrorCode` 하나로 만든다. 업무 예외는 모두 부모 `CodedException` 을 상속하고, `GlobalExceptionHandler` 는 그 부모 하나로 받는다. README·CLAUDE.md·docs 는 같은 작업에서 빠짐없이 갱신한다.

발단은 파생 프로젝트 b2b 의 같은 결함이다(공통 예외의 문자열 code 를 핸들러가 버림, 예외마다 몸통이 같은 핸들러를 한 쌍씩 둠, HTTP 상태를 클래스와 code 가 따로 정해 어긋남). 스켈레톤 3종을 진단한 결과 셋 모두에 같은 계열의 결함이 있다.

| 결함 | public-api | internal-api | batch | asp-net-core |
|---|---|---|---|---|
| 문자열 code 를 받아 놓고 버린다 | 있음 | 있음 | 있음 | 없음 |
| 몸통이 같은 핸들러 반복 | 있음 (인증 예외 10종) | 경미 (공통 예외 3종) | 있음 (예외 5종) | 없음 |
| 응답 본문 `status` 가 HTTP 상태와 다름 | 있음 | 있음 | 없음 | 없음 |
| 핸들러가 없어 500 으로 나가는 업무 예외 | 없음 | 없음 | 있음 | 없음 |
| 문서가 존재하지 않거나 쓰이지 않는 `ExceptionCode` 를 규칙으로 적음 | 있음 | 있음 | 있음 | 없음 |

## 2. 접근법

1. 부모 `CodedException(errorCode, message, cause)` 를 둔다. 이름은 asp-net-core 형제와 같다.
2. 공통 예외(`ClientBadRequestException`·`ItemNotFoundException` 등)는 부모를 상속하고 기본 `ErrorCode` 만 정한다. 문자열 code 통로와 쓰이지 않는 `ErrorMessageService` 계열을 없앤다.
3. errorCode 를 싣던 전용 예외(public 인증 예외, batch Job 예외)도 부모를 상속하고, 몸통이 같은 핸들러를 부모 핸들러 하나로 합친다. 응답 본문 모양이나 노출 정책이 다른 예외만 전용 핸들러를 유지한다.
4. 모든 핸들러가 `errorCode.status` 로만 HTTP 상태를 정한다. public·internal 은 이를 위해 `ErrorCode` 의 status 값을 실제 HTTP 상태에 맞춘다 — HTTP 상태는 바뀌지 않고 본문 `status`·구분 코드만 바뀐다. batch 는 이미 `errorCode.status` 로 응답하므로 기존 응답이 바뀌지 않는다. 예외로, 핸들러가 없어 500 으로 나가던 batch `ItemNotFoundException`·`BatchProcessException` 은 각자 코드(404 `COMMON_002`·500 `BATCH_001`)로 응답하게 된다.
5. 불변식을 테스트로 고정하고 장치 B 에 등록한다 — 코드의 status 범위·구분 코드 유일성(3레포), 본문 `status` = HTTP 상태(public·internal. batch `ErrorResponseModel` 에는 `status` 필드가 없다). 공통 예외 파일은 장치 A 표면으로 등록한다.

## 3. 파생 영향도 분류 — 규약 변경

- 표면: `exception/` 공통 클래스 시그니처, `enums/ErrorCode.kt` 값, `GlobalExceptionHandler` 의 응답 규칙, 각 레포 `CLAUDE.md`·`README.md` 의 예외 규칙.
- 형제 스켈레톤 동시 반영: public-api · internal-api · batch 를 같은 작업에서 반영한다. asp-net-core 는 수동 대조 대상이고 판정은 **해당 없음**이다(이미 `CodedException` 부모 + 단일 핸들러 + `ErrorCode.Status` 하나로 상태를 정한다).
- 기존 파생 프로젝트: **반영하지 않는다** (사용자 결정, 2026-10-26). 신규 생성 프로젝트만 받는다. 기존 파생 레포에 같은 결함이 복제돼 있을 수 있는 잔여 위험은 사용자가 수용했다. 반영 대상 레포·시점·담당은 없음으로 확정한다.

## 6. 범위

- 포함: Kotlin 3종의 `exception/`·`enums/ErrorCode.kt`·`handler/GlobalExceptionHandler.kt`·이를 쓰는 샘플 코드와 테스트, 각 레포 README·CLAUDE.md·docs, SKELETON `CLAUDE.md`·`AGENTS.md`·`docs/contract-surfaces.md`.
- 제외: asp-net-core 코드(해당 없음), 기존 파생 프로젝트(사용자 결정).
- 범위에서 확정 제외하고 사용자 판단을 요청하는 항목 — 이 작업의 종료 보고에서 질문한다. 둘 다 고치면 응답 코드가 바뀌어 이번 목적(상태를 정하는 곳을 하나로)과 별개의 계약 변경이다.
  - 스택 간 구분 코드 불일치 — asp-net-core `UNAUTHORIZED_ERROR` G015 · `CONFLICT_ERROR` G013, Kotlin public G007A · G008A. asp `ErrorCode.cs` 주석은 「Spring 과 같다」고 적는다.
  - `MissingRequestHeaderException` 이 `REQUEST_BODY_MISSING_ERROR`(G002)로 응답한다(의미상 G012).

## 1. 목적과 범위

HTTP 상태와 구분 코드를 정하는 곳을 `ErrorCode` 하나로 만든다. 업무 예외는 모두 부모 `CodedException` 을 상속하고, 핸들러는 그 부모 하나로 받는다. 고치는 결함과 범위는 설계 계획 §1·§6, 동작 요구사항은 레포별 기획서가 정본이다. 이 문서는 파일·시그니처·순서를 정한다.

## 2. 파생 영향도 분류 — 규약 변경

규약 표면: `exception/` 공통 클래스 시그니처, `enums/ErrorCode.kt` 값, `GlobalExceptionHandler` 의 응답 규칙, 각 레포 `CLAUDE.md`·`README.md` 의 예외 규칙.

| 대상 | 판정 |
|---|---|
| public-api | 반영 |

### 2.2 기존 파생 프로젝트

- 반영하지 않는다 (사용자 결정, 2026-10-26). 신규 생성 프로젝트만 변경을 받는다.

## 3. public-api · internal-api

`exception/` 의 공통 파일 5개(§3.1)는 `scripts/sibling-diff.sh` `full` 모드의 정규화(package·import 줄 제거, base package 치환) 뒤 두 레포가 같다.

### 3.1 예외 클래스

`exception/CodedException.kt` (신규):
```kotlin
package <base>.exception

import <base>.enums.ErrorCode

/**
 * 상태·구분 코드를 [errorCode] 하나가 정하는 예외의 부모. `GlobalExceptionHandler` 가 이 타입 하나로 받는다.
 *
 * 새 업무 코드가 필요하면 `ErrorCode` 에 항목을 추가하고 `throw CodedException(ErrorCode.X)` 로 던진다.
 * 같은 코드를 여러 곳에서 던지거나 `catch` 로 구분해야 할 때만 하위 클래스를 만든다.
 * [message] 는 4xx 응답의 `reason` 으로 나가므로 사용자에게 보여도 되는 문장으로 쓴다.
 */
open class CodedException(
    val errorCode: ErrorCode,
    message: String = errorCode.message,
    cause: Throwable? = null,
) : RuntimeException(message, cause)
```

공통 예외 — 기본 코드만 정한다. 문자열 code·`replaceValues`·보조 생성자를 없앤다.

| 파일 | 선언 |
|---|---|
| `exception/ClientBadRequestException.kt` | `open class ClientBadRequestException(message: String, cause: Throwable? = null) : CodedException(ErrorCode.BAD_REQUEST_ERROR, message, cause)` |
| `exception/ItemNotFoundException.kt` | `open class ItemNotFoundException(message: String, cause: Throwable? = null) : CodedException(ErrorCode.NOT_FOUND_ERROR, message, cause)` |
| `exception/InvalidRequestParameterException.kt` | `open class InvalidRequestParameterException(message: String = "유효하지 않은 요청 파라미터 입니다.") : ClientBadRequestException(message)` |
| `exception/ApiCallException.kt` | `class ApiCallException(message: String = "외부 API 호출에 실패했습니다.", errorCode: ErrorCode = ErrorCode.EXTERNAL_API_ERROR, cause: Throwable? = null) : CodedException(errorCode, message, cause)` — `httpStatus` 프로퍼티 삭제 |

### 3.4 `handler/GlobalExceptionHandler.kt`

- 생성자 주입 `errorMessageService` 를 없앤다. companion 의 `HTTP_STATUS_*` 상수를 없앤다.
- 모든 핸들러는 다음 private 함수로 응답한다. HTTP 상태를 정하는 곳은 `errorCode.status` 하나다.
  ```kotlin
  private fun respond(errorCode: ErrorCode, reason: String?): ResponseEntity<ErrorResponseModel> =
      ResponseEntity(ErrorResponseModel.of(errorCode, reason), HttpStatus.valueOf(errorCode.status))
  ```
- `@ExceptionHandler(CodedException::class)` 하나가 `ItemNotFoundException`·`ClientBadRequestException`·`ApiCallException` 핸들러(public 은 인증 예외 핸들러 10개 포함, §4)를 대신한다.
  ```kotlin
  @ExceptionHandler(CodedException::class)
  protected fun handleCodedException(ex: CodedException): ResponseEntity<ErrorResponseModel> {
      if (ex.errorCode.status >= 500) {
          logger.error("{} {}", ex.errorCode.divisionCode, ex.javaClass.simpleName, ex)
      } else {
          logger.warn("{} {}: {}", ex.errorCode.divisionCode, ex.javaClass.simpleName, ex.message)
      }
      return respond(ex.errorCode, ex.message)
  }
  ```
- 프레임워크 예외 핸들러(검증·Jackson·`NoHandlerFound`·`NoResourceFound`·`HttpClientErrorException.BadRequest`·`NullPointerException`·`NoSuchElementException`·`IOException`·`JsonParseException`·`IllegalArgumentException`·`Exception`)는 지금의 `ErrorCode` 선택과 로그를 유지하고 `respond` 로 응답한다.
- `WebClientRequestException`(public 만) → `respond(ErrorCode.SERVICE_UNAVAILABLE_ERROR, "External API unavailable")`.
- `AccessDeniedException`(public 만) — 익명 401 / 인증 403 분기를 유지하고 `respond` 로 응답한다.

## 4. public-api 전용 — 인증 예외

- `exception/auth/AuthException.kt` → `abstract class AuthException(errorCode: ErrorCode, message: String, cause: Throwable? = null) : CodedException(errorCode, message, cause)`. 직접 생성처는 0건이다.
- 하위 예외는 생성자 `(message: String, cause: Throwable? = null)` 를 유지하고 코드만 고정한다. 호출부는 바뀌지 않는다.

| 예외 | errorCode | 응답 (지금과 같음) |
|---|---|---|
| `AuthenticationException` · `UnauthorizedException` · `InvalidTokenException` | `UNAUTHORIZED_ERROR` | 401 G007A |
| `ForbiddenException` · `AuthorizationException` | `FORBIDDEN_ERROR` | 403 G008 |
| `DuplicateUserException` · `DuplicateResourceException` | `CONFLICT_ERROR` | 409 G008A |
| `ResourceNotFoundException` | `NOT_FOUND_ERROR` | 404 G009 |
| `AccountLockedException` | `ACCOUNT_LOCKED_ERROR` | 423 AUTH001 |
| `MfaException(errorCode, message)` | 생성자 인자 — 기존 `val errorCode` 를 지우고 `AuthException(errorCode, message)` 로 넘긴다(프로퍼티는 부모가 갖는다) | MFA001~MFA006 |

- `GlobalExceptionHandler` 의 인증 예외 핸들러 10개를 삭제한다. 로그는 §3.4 규칙(4xx `warn`)을 따른다.
- `exception/oauth2/OAuth2Exception.kt` 는 바꾸지 않는다 — RFC 6749 본문이라 컨트롤러 전용 핸들러가 처리한다.

## 5. batch

`exception/CodedException.kt` (신규):
```kotlin
/**
 * 상태·코드를 [errorCode] 하나가 정하는 예외의 부모. `GlobalExceptionHandler` 가 이 타입 하나로 받는다.
 * [details] 는 응답 `details` 로 나간다 — 요청 값(위조 가능)을 담지 않는다.
 */
open class CodedException(
    val errorCode: ErrorCode,
    message: String = errorCode.message,
    val details: String? = null,
    cause: Throwable? = null,
) : RuntimeException(message, cause)
```

`enums/ErrorCode.kt` 추가:
- `ITEM_NOT_FOUND(HttpStatus.NOT_FOUND, "COMMON_002", "Item not found")`
- `BATCH_PROCESS_ERROR(HttpStatus.INTERNAL_SERVER_ERROR, "BATCH_001", "Batch process failed")`
- 불변식: 모든 항목의 status 는 4xx·5xx 이고 `code` 는 서로 다르다. 검출 `ErrorCodeContractTest`.

예외 전환 (생성자 인자는 유지, `val errorCode` 선언은 부모로 옮긴다):

| 예외 | 선언 |
|---|---|
| `InvalidApiKeyException(message = INVALID_API_KEY.message, cause = null)` | `CodedException(INVALID_API_KEY, message, cause = cause)` |
| `JobNotFoundException(jobName, message, cause)` | `CodedException(JOB_NOT_FOUND, message, "jobName: $jobName", cause)` |
| `JobExecutionNotFoundException(jobExecutionId, message, cause)` | `CodedException(JOB_EXECUTION_NOT_FOUND, message, "jobExecutionId: $jobExecutionId", cause)` |
| `ItemNotFoundException(message, cause)` + `(entityName, id)` | `CodedException(ITEM_NOT_FOUND, message, cause = cause)` |
| `BatchProcessException(message, cause = null)` | `CodedException(BATCH_PROCESS_ERROR, message, cause = cause)` — 문자열 `errorCode` 와 보조 생성자 삭제 |
| `ForbiddenException(message)` | `CodedException(FORBIDDEN, message)` |
| `InvalidJobParameterException(jobName, rejectedKeys, message)` | `CodedException(INVALID_REQUEST, message, "rejectedKeys=${rejectedKeys.sorted()}")` |

`handler/GlobalExceptionHandler.kt`:
- `@ExceptionHandler(CodedException::class)` 하나가 `InvalidApiKey`·`JobNotFound`·`JobExecutionNotFound` 핸들러를 대신한다. 본문 `ErrorResponseModel(code = errorCode.code, message = ex.message ?: errorCode.message, details = ex.details)`, 상태 `errorCode.status`. 로그 규칙은 §3.4 와 같다.
- `ForbiddenException`·`InvalidJobParameterException` 은 전용 핸들러를 유지한다 — 응답 `message` 가 `ex.message` 가 아니라 `errorCode.message` 다(어떤 Job 이 있는지·위조 값을 응답에 싣지 않는다). Forbidden 은 `details` 를 싣지 않고, InvalidJobParameter 는 `ex.details` 를 싣는다.
- `JobInstanceAlreadyCompleteException`·`JobRestartException`·`Exception` 핸들러는 그대로 둔다.

### 7.1 스윕과 hit별 판정

구현을 마친 뒤 아래 검색을 3레포(`-g '!build/**'`)와 SKELETON(`-g '!plans/done/**' -g '!plans/ing/kotlin-coded-exception/**'`)에 돌린다. hit 마다 `반영 / 해당 없음 / 보류(사유)` 를 `검증_리포트.md` 「스윕」 표(검색 패턴·대상 경로·hit 위치·판정)에 남긴다.

| 목적 | 패턴 (`-e` 나열) | 기대 |
|---|---|---|
| 삭제한 이름의 잔존 | `ExceptionCode` `ErrorMessageService` `ErrorMessageDto` `replaceValues` `HTTP_STATUS_` `httpStatus` `"9999"` `INSERT_ERROR` | hit 0. hit 가 있으면 반영 후 재검색 |
| 공통 예외 사용처 | `ClientBadRequestException\(` `ItemNotFoundException\(` `InvalidRequestParameterException\(` `ApiCallException\(` `BatchProcessException\(` | hit 마다 새 시그니처 반영 여부 판정 |

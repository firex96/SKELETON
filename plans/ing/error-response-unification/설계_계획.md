# 오류 응답 정리 2차 — 설계 계획

- 작성일: 2026-10-26
- 선행 작업: [`plans/done/kotlin-coded-exception/`](../../done/kotlin-coded-exception/) — 그 검증 리포트 §7 의 미결을 이관받았다
- 근거와 결정 이유: [`리뷰_이력.md`](리뷰_이력.md)

## 1. 목적

스켈레톤의 오류 응답이 **스택 사이에서 같은 코드를 쓰고, 응답 문구는 사용자에게 그대로 보여도 되는** 상태가 되게 한다. 선행 작업에서 범위 밖으로 남긴 다섯 항목을 사용자 결정대로 처리한다.

| 항목 | 지금 | 바뀐 뒤 |
|---|---|---|
| 1. 스택 간 구분 코드 | 인증 실패 Kotlin public G007A · asp G015, 충돌 G008A · G013 | Kotlin public 이 asp 에 맞춘다(G015 · G013). 공통 코드표와 대조 스크립트로 유지 |
| 2. 응답 문구 | 프레임워크 예외·5xx 의 `reason` 에 내부 메시지(클래스 이름·예외 메시지)가 실리고, `resultMessage`(코드의 고정 문구)에 `tools.jackson.core Exception`·`Null Point Exception` 같은 기술 문구가 있다 | 응답의 모든 문구(`reason`·`resultMessage`, batch 는 `message`·`details`)가 사용자에게 보여도 되는 문장. 내부 메시지는 로그에만 |
| 3. batch 없는 실행 조회 | 웹훅 500 `COMMON_999`(④ 런타임 관찰). 관리자 API 는 같은 `JobExplorer.getJobExecution` 을 거치므로 같은 예외로 500 이 될 것으로 보며(구현 첫 단계에서 재현), 코드상 null 분기는 빈 본문 404 다 | 둘 다 404 `JOB_002` 오류 모델 |
| 4. 헤더 누락 | 400 `REQUEST_BODY_MISSING_ERROR` G002 | 400 `NOT_VALID_HEADER_ERROR` G012 |
| 5. 리뷰 제안 | — | 타당한 것(a·b·d·e·f)만 반영, c 는 기각 — §3 |

## 2. 사용자 결정 (2026-10-26)

- 코드 통일 방향은 Kotlin → asp. asp 가 빈 번호를 차례로 썼고 Kotlin 의 `A` 접미 코드는 기존 번호 사이에 끼워 넣은 형태라 asp 쪽이 정리돼 있다. asp 는 그 레포에서 작업한다는 원칙과도 맞는다(asp 는 바꾸지 않는다).
- 재발 방지는 공통 코드표(정본) + 대조 스크립트.
- 응답 문구 정책은 「항상 사용자 문장」. `reason` 뿐 아니라 응답에 나가는 모든 문구에 적용한다(① 리뷰에서 `resultMessage` 의 기술 문구를 지적받아 범위를 명시했다).
- batch 는 웹훅·관리자 API 둘 다 404 `JOB_002`.
- 헤더 누락은 G012.
- 리뷰 제안은 검토해 타당한 것만.

## 3. 접근법

1. **코드 통일** — public `ErrorCode` 의 두 값만 바꾼다. SKELETON `docs/error-codes.md` 에 스택 공통 코드와 스택 전용 코드(번호 예약)를 정본으로 두고, `scripts/error-code-parity.sh` 가 public·internal `ErrorCode.kt` 와 asp `ErrorCode.cs` 를 정본과 대조한다(같은 이름의 status·구분 코드 일치, 같은 구분 코드의 다른 이름 금지).
2. **응답 문구** — `ErrorCode.message`(응답 `resultMessage`)를 사람이 읽는 제목으로 바꾼다. 공통 코드는 asp `ErrorCode.cs` 의 제목과 같은 값(`Bad Request`·`Unauthorized`·`Not Found`…)이고, 대조 스크립트가 이것도 대조한다. 핸들러는 `reason` 을 상황별 고정 문장(또는 검증 메시지 조합)으로 정한다. 문장은 public·internal 공용 `handler/ErrorReason.kt` 한 곳에 둔다. 업무 예외 4xx 는 지금처럼 예외 메시지를 싣는다. 모든 핸들러가 `respond(errorCode, reason, ex)` 한 곳으로 응답하고, 거기서 4xx `warn`·5xx `error`(스택) 로그를 남긴다. batch 는 5xx·프레임워크 예외의 `message`·`details` 에서 내부 메시지를 빼고 코드의 고정 문구를 쓴다.
3. **batch 조회** — `JobExplorer.getJobExecution` 이 없는 id 에 `EmptyResultDataAccessException` 을 던지는 것을 확장 함수 하나에서 「없음」으로 바꾸고, 웹훅·관리자 두 경로가 `JobExecutionNotFoundException` 으로 응답한다.
4. **헤더 누락** — 핸들러의 코드 선택을 G012 로.
5. **리뷰 제안 판정**

| 제안 | 판정 | 사유 |
|---|---|---|
| a. `ExampleWebClient` 가 연결 실패도 502 로 감싼다 | 반영 | 같은 실패가 경로에 따라 502·503 으로 갈린다. `WebClientUtil` 은 batch 와 공유하는 표면이라 클라이언트에서 원인 사슬로 판정하고, internal 에도 `WebClientRequestException` 핸들러를 둔다 |
| b. batch `ForbiddenException` 의 메시지 인자와 전용 핸들러 | 반영 | 호출부는 모두 기본 메시지를 쓴다. 인자를 없애면 타입이 노출을 막고 전용 핸들러가 필요 없다 |
| c. `ErrorCode.status` 를 `HttpStatus` 타입으로 | 기각 | `ErrorCodeContractTest` 가 이미 400~599 를 보장한다. 변경 범위(모든 항목·응답 모델·필터 체인)에 비해 얻는 것이 작고, asp 도 정수다 |
| d. 프레임워크 4xx 핸들러가 `error`+스택으로 로그 | 반영 | 2번의 `respond` 로그 규칙으로 일원화한다 |
| e. 테스트 파일에 최상위 클래스가 여럿 | 반영 | `OneClassPerFileConventionTest` 가 테스트 소스셋도 검사하게 해 근본을 막고, 위반 3파일을 나눈다 |
| f. `INTEGRATION_GUIDE.md` 의 성공 응답 래퍼 | 반영 | 코드에 없는 모양(`resultMsg`·`ApiResponse<T>`)이다. 실제 응답으로 교정한다 |

## 4. 파생 영향도 분류 — 규약 변경 (+ 결함 수정)

- 규약 표면: public `ErrorCode` 구분 코드(외부 응답 계약), 응답 문구 규칙(README·CLAUDE.md 「예외」), `handler/ErrorReason.kt`(신규 공통 표면), `OneClassPerFileConventionTest` 검사 범위(3레포 공통 규약 테스트), SKELETON 공통 코드표·대조 스크립트.
- 결함 수정: batch 없는 실행 조회 500, 헤더 누락 코드, 연결 실패 502/503 불일치.
- 형제 스켈레톤 동시 반영: public · internal · batch 같은 작업에서. asp-net-core 는 수동 대조 대상 — 1번은 **해당 없음**(이미 정본 값), 2번은 5xx `Detail` 은 이미 숨긴다. 4xx 프레임워크 오류(모델 바인딩 메시지)가 기술 문구를 실을 수 있는지는 **사용자 판단 요청 항목**이다 — asp 코드는 이 작업 범위 밖이고(asp 작업은 그 레포에서 한다) 확인 결과와 함께 종료 보고에서 질문한다. 미루는 이득: 이 작업의 반영 대상(Kotlin 3종)과 검증 경로를 섞지 않는다.
- 기존 파생 프로젝트: **반영하지 않고, 같은 결함의 복제 여부 스윕도 하지 않는다** (사용자 결정, 2026-10-26 — ① 리뷰 뒤 질문에 「스윕도 생략 (잔여 위험 수용)」). 결함 수정 항목(batch 없는 실행 조회 500, 헤더 누락 코드, 연결 실패 502/503)이 파생 레포에 복제돼 있을 잔여 위험은 사용자가 수용했다.

# 오류 응답 정리 2차 — 리뷰 이력

설계서([`설계_계획.md`](설계_계획.md) · [`구현_설계.md`](구현_설계.md))에 담긴 결정의 근거, 채택하지 않은 대안, 리뷰 라운드 기록을 둔다.

## 착수 전 결정 (2026-10-26, 사용자)

### 「코드 통일 방향」

- 사용자 질문: 「의미론적으로 더 맞는 건 없을 것 같고, 더 잘 정리된 게 asp 쪽이야? 스프링 쪽이야?」
- 판단: asp. 두 코드 모두 각 레포 첫 커밋에서 생겼다(Kotlin public `105ad54` 2026-10-14, asp `175cd97` 2026-10-15). asp 는 빈 번호 G013·G014·G015 를 차례로 썼다. Kotlin 은 `G007A`(Jackson G007 과 계정 잠금 AUTH001 사이)·`G008A`(권한 G008 뒤)로 기존 번호 사이에 끼워 넣었다.
- 채택하지 않은 대안: asp 를 Kotlin 에 맞추는 것. asp 응답이 바뀌고, asp 작업은 그 레포에서 한다는 워크스페이스 원칙과 어긋난다.

### 「응답 문구 정책」

- 결정: 항상 사용자 문장. 5xx 도 고정 문장을 싣는다.
- 채택하지 않은 대안: asp 처럼 5xx 는 `reason` 을 비우는 방식. 클라이언트가 5xx 에서 보여 줄 문구를 스스로 정해야 한다.

### 「batch 없는 실행 조회」

- 결정: 웹훅·관리자 API 둘 다 404 `JOB_002` 오류 모델.
- 근거: 요청한 대상이 없는 것이므로 404 가 맞다. 500 은 서버 잘못이라는 뜻이라 틀리다. 관리자 API 의 빈 본문 404 는 오류 응답 모델 규칙(모든 4xx 는 같은 모델)과 어긋난다.

### 「재발 방지」

- 결정: 공통 코드표(SKELETON `docs/error-codes.md`) + 대조 스크립트(`scripts/error-code-parity.sh`).
- 근거: asp `ErrorCode.cs` 주석은 「Spring 과 같다」고 적지만 확인하는 장치가 없어 어긋났다. 장치 A 의 `symbols` 모드는 `const val` 만 읽어 enum 항목과 C# 정적 필드를 대조할 수 없다.

### 「파생 스윕 생략」

- 결정(① 리뷰 뒤 질문): 기존 파생 프로젝트는 반영도 스윕도 하지 않는다. 결함 수정 항목이 복제돼 있을 잔여 위험을 사용자가 수용했다.

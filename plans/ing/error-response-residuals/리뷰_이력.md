# 오류 응답 정리 3차 — 리뷰 이력

설계서([`설계_계획.md`](설계_계획.md))에 담긴 결정의 근거, 채택하지 않은 대안, 리뷰 라운드 기록을 둔다.

## 착수 전 결정 (2026-10-26)

### 「asp 범위」

- 사용자 결정: 이번 작업에서 함께 고친다.
- 근거: 세 SPA 클라이언트(`angular api-error.ts`·`nuxt utils/auth.ts`·`sveltekit lib/auth.ts`)가 `errors` 값을 화면에 보여 줘, .NET 기본 문구가 실제 사용자에게 노출된다. 405·415 응답의 코드가 400 코드(G001)라 Kotlin 에 새 코드를 두면 스택 간 불일치가 커진다.

### 「상태 기반 일괄 처리」

- 사용자 결정: Spring `ErrorResponse` 예외는 그 HTTP 상태로, 코드는 상태에서 고른다. 새 공통 코드 G017~G020.
- 채택하지 않은 대안: 예외마다 전용 핸들러. 프레임워크 예외가 늘 때마다 핸들러를 더해야 하고, 빠뜨리면 다시 500 이 된다.

### 「asp 문구 언어」

- 결정(이 계획): 한국어, asp 업무 예외 문구와 같은 어조(「~어요」).
- 근거: asp 업무 예외 문구(`TwoFactorEndpoints`·`PasskeyEndpoints`·`UserAccountBizService`)가 이미 한국어 사용자 문장이고, Kotlin `ErrorReason` 도 한국어다. 같은 응답 안에서 `detail` 은 한국어, `errors` 는 영어가 되는 것을 피한다.
- 채택하지 않은 대안: 영어 고정 문장(`The value is invalid.`). 기술 정보는 사라지지만 업무 문구와 언어가 갈린다.

### 「범위 밖 개선」

- 사용자 결정: getJobExecution 직접 호출 금지 규약 테스트, 401·403 코드·문구 짝 단일화, 외부 API 5xx 문장 상태 기반 선택, INTEGRATION_GUIDE 경로 전면 교정 — 넷 다.

### 「파생 프로젝트」

- 처음 가정: 선행 작업에서 사용자가 수용한 「반영·스윕 생략」을 이어 적용한다 → ① 1라운드 Codex Major(선행 수용은 그 작업 항목만 대상).
- 사용자 답(2026-10-26): 「파생 프로젝트 아직 없어」. 기존 파생 반영·스윕은 대상이 없어 해당 없음이다.

### 「없는 API 경로」 (② 조사에서 발견)

- 최소 앱 실행 결과: Server 구성에서 없는 `/api/...` GET 은 SPA 폴백이 200 HTML 로 응답한다. 잘못된 메서드는 405 로 가리지 않는다.
- 판단: 범위에 넣는다. API 클라이언트가 오류 대신 HTML 200 을 받아 「상태와 코드가 항상 일치」 목표 밖의 응답이 나간다. 고치는 범위는 폴백 하나다.
- 방식 비교(② 1라운드 Codex 지적 뒤, 최소 앱 실행):
  - **A. 모든 메서드를 받는 `MapFallback("api/{**path}")`:** GET 전용 경로의 DELETE 가 404 로 바뀐다 — 405 를 가린다. 기각.
  - **B. GET·HEAD 전용 `MapMethods("api/{**path}")`:** 405 는 지키지만 엔드포인트가 하나 늘어난다. `POST /api/nothing` 은 405 다.
  - **C. SPA 폴백 패턴에 `regex(^(?!api(/|$)))` 제약:** 405 를 지키고 엔드포인트를 늘리지 않는다. `POST /api/nothing` 405 는 원래 폴백(.NET 10 은 GET·HEAD 만)에서 이미 그렇다. **채택.**

### 「503 문장」

- `AsyncRequestTimeoutException`(503)도 상태 기반 규칙상 외부 서비스 문장이 된다. 스켈레톤에 비동기 MVC 엔드포인트가 없어 받아들인다.
- 채택하지 않은 대안: 코드에 「외부」 플래그를 두는 것. 사용자가 상태 기반 선택을 골랐다.

### 「HandlerMethodValidationException」

- Spring 내장 메서드 검증(400)은 상태 기반 규칙으로 `BAD_REQUEST_ERROR` 와 일반 문장이 된다. 지금은 500 이다.
- 채택하지 않은 대안: 전용 핸들러로 `NOT_VALID_ERROR` 와 파라미터별 문구를 내는 것. 스켈레톤 컨트롤러는 `@Validated` 로 `ConstraintViolationException` 경로를 쓰므로 이 예외가 나지 않는다. 범위를 넓히지 않는다.

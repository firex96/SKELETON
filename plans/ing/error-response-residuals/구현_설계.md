### 1.1 `handler/ErrorReason.kt` (두 레포 package 외 동일 — 장치 A `full`)

- 더한다:
  ```kotlin
  const val METHOD_NOT_ALLOWED = "허용되지 않는 요청 방식입니다."
  const val NOT_ACCEPTABLE = "요청한 응답 형식을 제공할 수 없습니다."
  const val PAYLOAD_TOO_LARGE = "요청 본문이 너무 큽니다."
  const val UNSUPPORTED_MEDIA_TYPE = "지원하지 않는 요청 본문 형식입니다."

  /** 상태 기반으로 처리한 4xx 의 문장. */

      when (status) {
          401 -> AUTHENTICATION_REQUIRED
          403 -> ACCESS_FORBIDDEN
          404 -> PATH_NOT_FOUND

          406 -> NOT_ACCEPTABLE

  fun forServerError(status: Int): String = if (status in 502..504) EXTERNAL_SERVICE_ERROR else SERVER_ERROR
  ```

### 1.2 `enums/ErrorCode.kt`

- 항목 추가(기존 G016 뒤, G999 앞): `METHOD_NOT_ALLOWED_ERROR(405, "G017", "Method Not Allowed")` · `NOT_ACCEPTABLE_ERROR(406, "G018", "Not Acceptable")` · `PAYLOAD_TOO_LARGE_ERROR(413, "G019", "Payload Too Large")` · `UNSUPPORTED_MEDIA_TYPE_ERROR(415, "G020", "Unsupported Media Type")`. 생성자 인자 순서는 기존 항목과 같다.
- `companion object`:
  ```kotlin
  companion object {
      /** 상태 기반 처리의 대표 코드. 첫 일치가 아니라 이 목록이 정한다(400 은 BAD_REQUEST_ERROR). */
      private val BY_STATUS: Map<Int, ErrorCode> = listOf(/* 레포별 목록 */).associateBy { it.status }

      /** 목록 밖 상태는 4xx → BAD_REQUEST_ERROR, 5xx → INTERNAL_SERVER_ERROR — 응답 HTTP 상태도 그 코드의 상태가 된다. */
      fun fromStatus(status: Int): ErrorCode = BY_STATUS[status] ?: if (status >= 500) INTERNAL_SERVER_ERROR else BAD_REQUEST_ERROR
  }
  ```
  - public 목록: `BAD_REQUEST_ERROR, UNAUTHORIZED_ERROR, FORBIDDEN_ERROR, NOT_FOUND_ERROR, METHOD_NOT_ALLOWED_ERROR, NOT_ACCEPTABLE_ERROR, CONFLICT_ERROR, PAYLOAD_TOO_LARGE_ERROR, UNSUPPORTED_MEDIA_TYPE_ERROR, ACCOUNT_LOCKED_ERROR, INTERNAL_SERVER_ERROR, EXTERNAL_API_ERROR, SERVICE_UNAVAILABLE_ERROR`
  - internal 목록: 위에서 `UNAUTHORIZED_ERROR`·`CONFLICT_ERROR`·`ACCOUNT_LOCKED_ERROR` 를 뺀 것
  - `associateBy` 는 같은 상태가 둘이면 뒤가 이긴다. 그래서 `BY_STATUS` 를 만들 때 `check(map.size == list.size)` 로 상태 중복을 거부한다 — 겹치면 enum 초기화가 실패해 모든 테스트가 실패한다. 기대 표 단언(§1.4)은 최종 매핑 결과를 검증한다.

### 1.3 `handler/GlobalExceptionHandler.kt`

- `respond` 에 헤더 인자를 더하고, 5xx 문장을 상태로 고른다:
  ```kotlin
  private fun respond(
      errorCode: ErrorCode,
      reason: String,
      ex: Exception,
      headers: HttpHeaders = HttpHeaders.EMPTY,
  ): ResponseEntity<ErrorResponseModel> {
      // 로그는 지금과 같다
      val body = ErrorResponseModel.of(errorCode, if (serverError) ErrorReason.forServerError(errorCode.status) else reason)
      return ResponseEntity(body, headers, HttpStatus.valueOf(errorCode.status))
  }
  ```
- 캐치올:
  ```kotlin
  /**
   * Spring 기본 예외(`ErrorResponse` — 405·406·413·415·503 등)는 그 상태와 그 상태의 코드로 응답한다. 상태가 보존되면 `Allow`·`Accept` 같은
   * 예외 헤더도 싣는다. 그 밖의 예외는 500.
   */
  @ExceptionHandler(Exception::class)
  protected fun handleAllExceptions(ex: Exception): ResponseEntity<ErrorResponseModel> {
      if (ex is ErrorResponse) {
          val status = ex.statusCode.value()
          val errorCode = ErrorCode.fromStatus(status)
          val headers = if (errorCode.status == status) ex.headers else HttpHeaders.EMPTY
          return respond(errorCode, ErrorReason.forStatus(errorCode.status), ex, headers)
      }
      return respond(ErrorCode.INTERNAL_SERVER_ERROR, ErrorReason.SERVER_ERROR, ex)
  }
  ```
- 클래스 KDoc 에 「처리하지 않는 프레임워크 예외는 상태 기반」 한 줄을 넣는다. 다른 핸들러는 바꾸지 않는다(public `AccessDeniedException` 만 §2).

- 새 핸들러:
  ```kotlin

  fun handleMethodArgumentTypeMismatchException(ex: MethodArgumentTypeMismatchException): ResponseEntity<ErrorResponseModel> =

  /** 본문 형식 오류 — 예외 메시지(타입·위치)는 로그에만. */
  @ExceptionHandler(HttpMessageNotReadableException::class)
  ```

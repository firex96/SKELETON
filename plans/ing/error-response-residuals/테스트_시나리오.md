# 테스트 시나리오 — 오류 응답 정리 3차

상위 계획: [`설계_계획.md`](설계_계획.md). 모든 오류 응답 시나리오는 두 가지를 함께 단언한다. 「HTTP 상태 = 본문 코드의 상태」와 「문구에 기술 정보가 없다」다. 기술 정보는 클래스·패키지·타입 이름, 프레임워크·하위 라이브러리·외부 응답의 내부 메시지, `Path: $`, `LineNumber`, 프레임워크 오류 문장에 되돌린 요청 값을 말한다. 사용자 문장으로 쓴 업무 예외 4xx 메시지는 기존 규칙대로 응답에 싣는다.

## 1. Kotlin public·internal — 상태 기반 처리 (통합, `FrameworkStatusResponseIntegrationTest`)

테스트 컨트롤러(`TestFrameworkStatusController`, `/test/framework-status`)의 엔드포인트에 MockMvc 로 요청한다. 1.8 회귀는 기존 `GlobalExceptionHandlerTest` 가 맡는다.

| # | 요청 | 기대 |
|---|---|---|
| 1.1 | GET 전용 경로에 `DELETE` | 405 · `METHOD_NOT_ALLOWED_ERROR` · G017 · reason 「허용되지 않는 요청 방식입니다.」 · `Allow` 헤더에 `GET` |
| 1.2 | JSON 전용 POST 에 `Content-Type: text/plain` | 415 · `UNSUPPORTED_MEDIA_TYPE_ERROR` · G020 · `Accept` 헤더 |
| 1.3 | `produces = text/plain` 경로에 `Accept: application/json` | 406 · `NOT_ACCEPTABLE_ERROR` · G018 — 본문 단언 필수(오류 본문 JSON 은 협상 가능) |
| 1.4 | `MaxUploadSizeExceededException` 을 던지는 경로 | 413 · `PAYLOAD_TOO_LARGE_ERROR` · G019 |
| 1.5 | `AsyncRequestTimeoutException` 을 던지는 경로 | 503 · `SERVICE_UNAVAILABLE_ERROR` · G016 · reason 외부 서비스 문장 |
| 1.6 | `ResponseStatusException(I_AM_A_TEAPOT)` | 400 · `BAD_REQUEST_ERROR` · G001 (목록 밖 4xx → 대체, HTTP 도 400) · 헤더 미전달 |
| 1.7 | `ResponseStatusException(HttpStatus.GATEWAY_TIMEOUT)` | 500 · `INTERNAL_SERVER_ERROR` · G999 (목록 밖 5xx) · reason `SERVER_ERROR`. 이 경우 504 상태가 아니라 코드 상태 500 으로 바뀌므로, P3 의 504 분기는 `fromStatus` 를 거치지 않는 코드에만 해당한다 |
| 1.8 | 기존 전용 핸들러(없는 경로 404, 바인딩, 헤더 누락) | 지금 값 그대로(회귀) |
| 1.9 | 모든 위 응답 본문 | `Exception`·`org.springframework`·`com.rex` 미포함(`bodyHasNoInternals`) |

단위(`ErrorCodeContractTest` 또는 새 `ErrorCodeFromStatusTest`):
- 목록의 각 상태가 그 상태의 코드를 돌려준다.
- 목록 밖 4xx 는 400 코드, 5xx 는 500 코드를 돌려준다.
- 모든 반환 코드의 `status` 가 HTTP 표준 상태다.

## 3. Kotlin — 5xx 문장 (`ErrorReason.forServerError`)

- 단위: 상태 500 → `SERVER_ERROR`, 502·503 → `EXTERNAL_SERVICE_ERROR`. 504 는 코드가 없으므로 `forServerError` 단위 테스트에서 상태 502~504 범위 판정을 직접 확인한다(가짜 코드 대신 범위 함수를 테스트할 수 있게 ③ 에서 시그니처를 정한다).
- 통합: 기존 외부 API·캐치올 5xx 시나리오의 reason 이 그대로다(회귀).

## 8. 런타임

- public 을 기동(`docker compose up -d --wait`, 실행마다 만든 `MFA_SECRET_ENCRYPTION_KEY`)해 실제 요청을 보낸다.
  - 유효한 access token(가입 → 로그인으로 얻은 것)을 실어 `DELETE /products/1` → 405 G017 과 없는 경로 → 404 를 확인한다. 인증 없이 보내면 보안 필터가 먼저 401 로 끝낸다(`anyRequest().authenticated()`).
  - `POST /auth/login`(permitAll) `text/plain` → 415 G020
  - 토큰 없는 요청 → 401 짝 — 별도 검증
- batch 를 기동해 `GET /api/v1/jobs/executions/abc` → 400 을 확인한다.
- asp Server 는 FunctionalTests 로 대신한다. 기동하려면 DB·Redis 가 필요하고, 함수 테스트가 실제 파이프라인(`WebApplicationFactory`)을 쓴다.
- 문서: INTEGRATION_GUIDE 의 경로·모델을 실제 엔드포인트와 대조한다. 기동한 public 에 가이드의 주요 요청(가입 201 → 로그인 200 → `/users/me` → 갱신 → 로그아웃 204)을 순서대로 보내 응답 모양이 문서와 같은지 확인한다.

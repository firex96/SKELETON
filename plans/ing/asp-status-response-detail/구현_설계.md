# asp 상태 코드 응답의 detail — 구현 설계

<!-- CHECKPOINT3: required -->

- 목적: asp-net-core 의 4xx 오류 응답은 어디서 만들어졌든 화면에 그대로 보여도 되는 `detail` 문장을 갖는다. 5xx 와 검증 실패는 지금 계약 그대로다.
- 출처: 오류 응답 정리 3차 체크포인트 ④ 의 비차단 지적(`plans/done/error-response-residuals/`). 다음 작업으로 고른 것은 사용자 결정이다(2026-10-27). 근거: [`리뷰_이력.md`](리뷰_이력.md)
- 경로 표기는 `../asp-net-core-skeleton` 레포 루트 기준이다. `Common/` 은 `src/common/AspNetCoreSkeletonApplication.Common/` 이다.

## 1. 티어 · 파생 영향도

- 티어: 체크포인트 ③·④. 단일 스켈레톤 안의 결함 수정이고 새 규약이 없다. SKELETON 핵심 규칙 「예외」의 「그 밖은 고정 문장」에 asp 구현을 맞춘다.
- 분류: 보안·결함 수정. 응답 계약이 공통 규칙과 어긋난 결함이다.
- 파생 스윕: 해당 없음. 기존 파생 프로젝트가 없다(사용자 확인 2026-10-26).
- Kotlin 형제 대조: 해당 없음. public·internal 은 `ErrorReason.forStatus` 로, batch 는 `errorCode.message` 로 이미 모든 응답에 문장을 싣는다.
- SKELETON 지침·코드표: 해당 없음. 규칙 문장이 이미 맞고, 오류 코드는 바꾸지 않는다.

## 2. 계약

| 응답 | `detail` |
|---|---|
| 업무 예외 4xx (`CodedException`) | 예외 메시지 (변경 없음) |
| `detail` 을 직접 준 `TypedResults.Problem(...)` (로그인 실패·잠김 등) | 준 문장 (변경 없음) |
| 검증 실패 (`HttpValidationProblemDetails`) | 없음 — 문장은 `errors` (변경 없음) |
| 5xx 전부 | 없음 (변경 없음) |
| 그 밖의 4xx — `BadHttpRequestException`, `UseStatusCodePages`(401·403·404·405·406·415), 컨트롤러 `NotFound()`·`Forbid()`·`StatusCode(4xx)`, 최소 API `TypedResults.NotFound()`·`Forbid()`, 코드가 없는 4xx(418 → 400) | `ErrorMessages.ForStatus(최종 상태)` |

- 불변식: 응답 상태가 400~499 이고 검증 실패가 아니면 `detail` 은 null 이 아닌 사용자 문장이다.
- 401·403 의 문장은 SPA 세 클라이언트 `messageOf` 의 대비 문장과 글자 그대로 같다. 그래서 401·403 화면 문구는 바뀌지 않는다.

## 3. 변경

### 3.1 `Common/Web/ErrorMessages.cs`

`ForStatus` 의 `switch` 에 다음 다섯 행을 더한다. 기존 행(405·406·413·415·기본)은 그대로다.

```csharp

403 => "이 작업을 할 권한이 없어요.",
404 => "요청한 대상을 찾을 수 없어요.",
409 => "요청이 지금 상태와 맞지 않아요.",
423 => "요청한 대상이 잠겨 있어요.",
```

- 행은 상태 오름차순으로 둔다.
- 클래스 주석의 「프레임워크가 만든 4xx 에 싣는 사용자 문장」은 그대로 맞다.

### 3.2 `Common/Web/ProblemDetailsExtensions.cs`

다음 메서드를 `AddErrorCodeIfMissing` 아래에 더한다.

```csharp
/// <summary>
/// 문장이 없는 4xx(상태 코드 응답, 컨트롤러의 NotFound() · Forbid(), 프레임워크 예외)에 상태별 사용자 문장을 싣는다.
/// 검증 실패는 errors 가 문장이고, 5xx 는 내부 사정이라 싣지 않는다. 이미 있는 detail 은 그대로 둔다.
/// </summary>
public static void AddDetailIfMissing(this ProblemDetails problemDetails)
{
    if (problemDetails.Detail is null
        && problemDetails is not HttpValidationProblemDetails
        && problemDetails.Status is >= StatusCodes.Status400BadRequest and < StatusCodes.Status500InternalServerError)
    {
        problemDetails.Detail = ErrorMessages.ForStatus(problemDetails.Status.Value);
    }
}
```

### 3.3 `Common/Web/WebServiceCollectionExtensions.cs`

`CustomizeProblemDetails` 람다에서 `AddErrorCodeIfMissing(context.HttpContext)` 바로 다음 줄에 `context.ProblemDetails.AddDetailIfMissing();` 를 부른다.

## 8. 2차 — 5xx `detail` 강제 제거 (사용자 지시 2026-10-27)

1차(§1~§7)는 커밋 `e6551be` 로 들어갔다. 사용자는 1차의 후속 과제 두 가지를 같은 작업에서 정리하라고 지시했다. 하나는 5xx `detail` 강제 제거이고, 다른 하나는 지난 작업의 CHANGELOG 누락이다.

### 8.1 티어 · 파생 영향도

- 5xx `detail` 강제 제거: 체크포인트 ③·④. 단일 스켈레톤 안의 보안·결함 수정이다. 앱이 5xx 에 직접 준 내부 문장이 응답으로 나갈 수 있는 구멍을 막는다.
- CHANGELOG 보충: 문서라서 체크포인트 ④ 만 거친다.
- 파생 스윕: 해당 없음. 파생 프로젝트가 없다(사용자 확인 2026-10-26).
- 스켈레톤 안 스윕: `rg -n -e 'statusCode: StatusCodes.Status5' -e 'Status500' -e 'Status502' -e 'Status503' src --glob '*.cs'` 로 5xx 에 `detail` 을 직접 주는 코드를 찾는다. 검증 리포트에 hit 별 판정을 남긴다.
- Kotlin 형제 대조: 해당 없음. public·internal 의 5xx `reason` 은 `ErrorReason.forServerError` 의 고정 문장이고, batch 는 `errorCode.message` 다. 앱이 직접 준 문장이 나가는 경로가 없다.

### 8.2 계약 (§2 표의 5xx 행을 바꾼다)

| 응답 | `detail` |
|---|---|
| 5xx 전부 — 예외 처리기, 상태 코드 응답, 앱이 직접 준 `Problem(detail: …, statusCode: 5xx)`·`TypedResults.Problem(…)` 포함 | 없음. 공통 단계가 지운다 |

불변식이 하나 더 생긴다: 응답 상태가 500~599 이면 `detail` 은 없다. 이 불변식과 1차의 4xx 불변식은 요청의 `Accept` 와 무관하게 성립한다.

- 보장 경계는 `IProblemDetailsService` 다. 상태 코드 페이지, 예외 처리기, 최소 API `ProblemHttpResult` 가 모두 이 서비스로 쓴다.
- 기본 서비스는 맞는 writer 가 없으면 `false` 를 돌려준다. 기본 writer 는 `Accept` 가 JSON 을 받지 않을 때(예: `Accept: text/html` 만) 거절한다. 그러면 최소 API 는 `CustomizeProblemDetails` 를 거치지 않은 원래 객체를 JSON 으로 쓴다. 이때 코드가 없고 5xx `detail` 이 남는다.
- 그래서 서비스를 스켈레톤 구현으로 바꾼다(8.3).
- MVC `ControllerBase.Problem()` 은 생성 단계(`ProblemDetailsFactory`)에서 customize 를 거치므로 원래부터 안전하다. (근거: 리뷰_이력.md 「체크포인트 ③ 3라운드」)

### 8.3 변경

**`Common/Web/ProblemDetailsExtensions.cs`**

`AddDetailIfMissing` 을 `NormalizeDetail` 로 바꿔, 4xx 문장 채우기와 5xx 제거를 한 메서드가 맡는다.

```csharp
/// <summary>
/// detail 을 상태에 맞춘다. 5xx 는 내부 사정이라 누가 넣었든 지운다(앱이 Problem(detail: …) 로 줘도).
/// 문장이 없는 4xx(상태 코드 응답, 컨트롤러의 NotFound() · Forbid(), 프레임워크 예외)에는 상태별 사용자 문장을 싣는다.
/// 검증 실패는 errors 가 문장이고, 이미 있는 4xx detail 은 그대로 둔다.
/// </summary>
public static void NormalizeDetail(this ProblemDetails problemDetails)
{
    if (problemDetails.Status is >= StatusCodes.Status500InternalServerError)
    {
        problemDetails.Detail = null;
    }
    else if (problemDetails.Detail is null
        && problemDetails is not HttpValidationProblemDetails
        && problemDetails.Status is >= StatusCodes.Status400BadRequest)
    {
        problemDetails.Detail = ErrorMessages.ForStatus(problemDetails.Status.Value);
    }
}
```

- 상태 비교는 `is >=` 패턴으로 쓴다. 그래야 nullable 흐름 분석이 `Status.Value` 를 null 아님으로 본다(CS8629 경고 0).

- `AddErrorCodeIfMissing` 이 먼저 돌므로 `Status` 는 코드의 상태로 맞춰져 있다. 코드가 없는 상태도 4xx 400·5xx 500 으로 바뀐다.

**새 파일 `Common/Web/ProblemDetailsDispatcher.cs`** (`internal sealed class ProblemDetailsDispatcher : IProblemDetailsService`)

- 이름: asp 명명 규약(`NamingConventionTests.BareServiceSuffix_IsNotUsed`)은 맨 `Service` 접미사를 막는다. 그래서 하는 일(writer 를 골라 넘기고, 없으면 대비 경로로 쓴다)을 이름으로 쓴다. (근거: 리뷰_이력.md 「체크포인트 ③ 4라운드」)

- 생성자 인자: `IEnumerable<IProblemDetailsWriter> writers`, `IOptions<ProblemDetailsOptions> options`, `IOptions<Microsoft.AspNetCore.Http.Json.JsonOptions> jsonOptions`. `writers` 는 배열로 한 번 만든다.
- `TryWriteAsync(context)`:
  1. 기본 서비스와 같이 writer 를 등록 순서대로 돌고, 처음으로 `CanWrite` 가 참인 writer 로 쓰고 `true` 를 돌려준다.
  2. 맞는 writer 가 없으면 대비 경로로 쓰고 `true` 를 돌려준다.
     - 기본값: `Status ??= Response.StatusCode`, `Title ??= ReasonPhrases.GetReasonPhrase(Status)`.
     - 정규화: `options.Value.CustomizeProblemDetails?.Invoke(context)`. 코드, 상태 대체, `NormalizeDetail`, traceId 가 모두 여기서 적용된다.
     - 쓰기: `Response.WriteAsJsonAsync(problemDetails, jsonOptions.Value.SerializerOptions.GetTypeInfo(problemDetails.GetType()), "application/problem+json", RequestAborted)`.
- `WriteAsync(context)`: `TryWriteAsync` 를 부른다. 대비 경로가 있어 언제나 `true` 다.
- 클래스 주석에 이유를 적는다. 기본 서비스는 맞는 writer 가 없으면 실패하고, 그때 최소 API 가 정규화 없이 원래 객체를 쓴다.

**`Common/Web/WebServiceCollectionExtensions.cs`**
- `AddProblemDetails(...)` 바로 뒤에 `services.Replace(ServiceDescriptor.Singleton<IProblemDetailsService, ProblemDetailsDispatcher>());` 를 둔다. `AddProblemDetails` 는 기본 서비스를 `TryAdd` 로 등록하고, 뒤에 오는 `AddControllers()` 는 writer 만 더한다.
- 호출을 `context.ProblemDetails.NormalizeDetail();` 로 바꾼다.
- 순서 주석은 그대로 둔다.
- 위쪽 설명 주석은 「문장이 없는 4xx 의 detail 을 붙이고(5xx 의 detail 은 지운다)」로 고친다.

**`Common/Web/GlobalExceptionHandler.cs`**
- `Detail = 5xx ? null : message` 는 그대로 둔다. 5xx 업무 예외의 메시지(`ApiCallException` 의 외부 응답 등)를 만든 곳에서 막는 1차 방어다. 앱이 `CustomizeProblemDetails` 를 바꿔도 처리기는 내부 메시지를 싣지 않는다.
- 클래스 주석의 `AddDetailIfMissing` 참조는 `NormalizeDetail` 로 바꾼다.

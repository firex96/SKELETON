# asp 상태 코드 응답의 detail — 리뷰 이력

## 「출처」

오류 응답 정리 3차의 체크포인트 ④ 자체 리뷰(`plans/done/error-response-residuals/`)가 비차단 지적을 하나 남겼다. 내용은 asp 상태 코드 응답(예외 없는 405·415 등)에 `detail` 문장이 없다는 것이다. 당시에는 기존 asp 계약(본문 없는 상태 응답은 `detail` 없음)이라 유지했다. Kotlin 형제는 같은 경우에 `reason` 문장을 싣는다. 사용자가 2026-10-27 다음 작업으로 이 항목을 골랐다.

## 「설계 결정」

- **401·403 문장을 SPA 대비 문장과 같게 둔 이유**
  - 세 SPA 의 `ApiError` 는 `detail ?? messageOf(status)` 로 문장을 고른다.
  - 서버 문장을 SPA 의 「로그인이 필요해요.」·「이 작업을 할 권한이 없어요.」와 같게 두면, 서버가 문장을 싣기 시작해도 401·403 화면 문구가 그대로다.
  - 다른 문장을 고르면 SPA 코드를 함께 바꾸거나 화면 문구 변화를 받아들여야 한다.
- **문장 채우기를 `CustomizeProblemDetails` 한 곳에 둔 이유**
  - 예외 처리기(`GlobalExceptionHandler`)도 `IProblemDetailsService.TryWriteAsync` 로 쓰므로 같은 customize 를 지난다.
  - 그래서 처리기의 `?? ErrorMessages.ForStatus` 를 지우면 상태 문장을 고르는 곳이 하나가 된다.
  - 처리기와 customize 두 곳에 같은 규칙을 두는 안은 채택하지 않았다.
- **SPA 코드를 고치지 않은 이유**
  - `messageOf` 는 ProblemDetails 가 아닌 응답(프록시·네트워크 오류 페이지)의 대비로 여전히 필요하다.
  - 서버 문장이 SPA 대비 문장과 같으니 고칠 동기가 없다.
- **`ErrorCode.ByStatus` 를 열지 않은 이유**
  - 단위 테스트는 400~499 를 돌며 `FromStatus(s).Status == s` 인 상태만 고르면 같은 목록을 얻는다.
  - 공개 범위를 넓힐 필요가 없다.

- 기본 서비스와 writer 의 동작은 .NET 10 원본(`ProblemDetailsService.cs`, `DefaultProblemDetailsWriter.cs`)으로 확인했다.
  - 기본 서비스는 writer 를 등록 순서대로 돌고, 처음으로 `CanWrite` 가 참인 writer 를 쓴다.
  - 기본 writer 는 Accept 가 없거나 JSON·`*/*` 를 포함하면 쓴다.

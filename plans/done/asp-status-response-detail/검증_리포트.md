네 관점(Reuse · Simplification · Efficiency · Altitude)으로 검토했다.

| 지적 | 판정 | 처리 |
|---|---|---|
| `FrameworkErrorResponseTests` 가 `AssertProblemAsync` 뒤에 `detail` 단언을 반복한다 (Simplification) | 반영 | 헬퍼가 `string? detail` 을 받아 함께 단언한다(null 이면 없어야 한다). 검증 실패 호출 6곳은 `AssertValidationProblemAsync` 로 묶었다. 그 결과 검증 실패 응답에 `detail` 이 없다는 것도 단언하게 됐다 |
| `ErrorMessages` 클래스 주석이 「프레임워크가 만든 4xx」만 말한다 (Simplification) | 반영 | 상태 코드 응답 · 컨트롤러 `NotFound()` 를 포함하게 고쳤다 |
| 코드 → 문장 순서가 호출 두 줄의 배치에만 기댄다 (Altitude) | 반영(주석) | 호출 지점에 순서 이유를 한 줄로 적었다. 둘을 묶는 새 메서드는 설계가 정한 구조를 바꾸므로 두지 않았다 |

| 5xx `detail` 제거도 공통 단계가 맡게 하자 (Altitude) | 건너뜀 | 앱이 `Problem(detail:…, statusCode: 500)` 로 직접 준 문장까지 지우는 동작 변경이라 승인된 설계 밖이다. 후속 과제(§8) |

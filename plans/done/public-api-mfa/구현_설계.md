# public-api 2차 인증(TOTP + 복구 코드) — 구현 설계

- 대상: `../spring-boot-public-api-skeleton` (기준 `main` `cacddc2`)
- 근거·결정 이력: [`리뷰_이력.md`](리뷰_이력.md)

## 1. 목적과 범위

비밀번호나 소셜 계정만 탈취되어서는 계정이 넘어가지 않도록 public-api 에 2차 인증을 넣는다. 함께 고치는 기존 결함 4건(§6)은 모두 2차 인증의 전제이거나 같은 경로에 있다.

| 항목 | 결정 |
|---|---|
| 2단계 수단 | TOTP(RFC 6238)와 1회용 복구 코드 10개. 메일·SMS 코드는 없다 |
| 기기 기억 | 없다. 2차 인증을 켠 사용자는 로그인할 때마다 2단계를 거친다 |
| 강제 | 없다. 사용자가 스스로 켠다. 관리자는 초기화만 한다 |
| 적용 경로 | 1단계 인증이 끝나는 모든 경로 — `POST /auth/login`, `POST /oauth2/login`, 소셜 브라우저 콜백, 네이티브 `POST /auth/oauth2/{p}/login` |

## 2. 파생 영향도 분류 — 스켈레톤 전용(기능 추가) + 보안·결함 수정(§6)

### 2.1 형제 스켈레톤 스윕 (2026-10-19)

| 대상 | 검색 패턴 | hit | 판정 |
|---|---|---|---|
| `../spring-boot-internal-api-skeleton/src` | `rg -i -l -e 'mfa' -e 'totp' -e 'two.?factor' -e 'otpauth'` / `rg -i -l -e 'PasswordEncoder' -e '/auth/login' -e 'fun login'` | 0 / 0 | 해당 없음 — 최종 사용자 로그인이 없다 |
| `../spring-batch-skeleton/src` | 같음 | 0 / 0 | 해당 없음 — 같은 이유 |
| `../asp-net-core-skeleton` (수동 대조) | `Web/TwoFactorEndpoints.cs` | — | 해당 없음 — 이미 TOTP·복구 코드가 있다. 그 레포에 TOTP 재사용 방지가 없다는 점은 §9 미결 |

§6 결함 4건(소셜 잠금 미적용, 비밀번호 변경 세션 미폐기, 로그인 감사 누락, `auth_time`)은 public-api 에만 있는 코드다. internal-api·batch 는 위 스윕에서 로그인·세션 코드가 hit 0 이라 해당 없다.

### 2.2 기존 파생 프로젝트

- 자동 전파 없음. 기존 파생 프로젝트는 자기 인증 코드를 갖고 있고, 이 기능을 원하면 수동으로 이식한다.
- 파생 프로젝트 스윕은 하지 않는다 — 직전 작업과 같은 사용자 결정(스켈레톤만)을 따른다. 리뷰 이력 「착수 전 결정」.
- 계약 변화: 2차 인증을 켠 사용자의 로그인이 202 challenge 를 받는다(켜지 않은 사용자는 그대로). `/user/password/change` 뒤 다른 세션이 폐기된다. id_token `auth_time` 값이 바뀐다. 로컬 실행에 환경변수 `MFA_SECRET_ENCRYPTION_KEY` 가 필요하다.

### 2.3 형제 공통 표면

새 파일은 public-api 전용 경로(`service/mfa/`·`util/Totp` 등)에 둔다. `sibling-diff.sh` 감시 표면(공통 명명표·conventions 절·`MapstructConfiguration` 등)은 바꾸지 않는다. `util/` 에 두는 `Totp`·`Base32` 는 public-api 에만 생기는 파일이라 대조 대상이 아니다.

## 3. 불변식

1. **`user_sessions` 행, 1st-party 토큰, 브라우저 SecurityContext 는 2단계를 통과한 뒤에만 만든다.** 2차 인증이 켜진 사용자의 1단계 통과는 Redis challenge 만 만든다(API·브라우저 공통, §5.3).
2. 따라서 `/oauth2/authorize`·refresh·`/auth/oauth2/{p}/link`·`/user/**` 는 별도 게이트를 두지 않는다. 이 경로들은 이미 만들어진 세션만 받는다.
3. 같은 TOTP 구간의 코드와 같은 복구 코드는 **한 번만** 통과한다(DB 조건부 UPDATE, §5.2).
4. challenge 는 성공 시 **한 번만** 소비된다(Redis 원자 연산). 서로 다른 유효 코드를 동시에 내도 세션은 하나만 발급된다.
5. 2차 인증 대상 계정의 실패 카운터는 **최종(2단계) 성공 때만** 초기화된다. 1단계 성공은 카운터를 건드리지 않는다. 2단계 실패는 비밀번호 실패와 같은 카운터를 올린다.
6. 2단계 제출은 코드를 보기 전에 challenge 존재·만료와 계정 잠금을 먼저 확인한다(API·브라우저 공통).

## 5. 2차 인증

### 5.1 등록·관리 API (커밋 6, 복구 코드는 커밋 7)

`controller/user/UserMfaController.kt` `@RequestMapping("/user/mfa")`, Bearer 인증 필수 → `UserMfaMappingService` → `MfaBizService`.

| 엔드포인트 | 요청 | 응답 | 실패 |
|---|---|---|---|
| `GET /user/mfa` | — | `MfaStatusModel{enabled, recoveryCodesLeft}` | — |
| `POST /user/mfa/totp/setup` | — | `MfaSetupModel{secret, otpauthUri}` — secret 은 Base32 를 4자씩 공백으로 끊는다. `otpauth://totp/{issuer}:{loginId}?secret=…&issuer=…&digits=6&period=30&algorithm=SHA1` | 이미 ACTIVE 면 409 `MFA_ALREADY_ENABLED` |
| `POST /user/mfa/totp/activate` | `{code}` | `MfaRecoveryCodesModel{recoveryCodes}`(커밋 7 부터 10개, 커밋 6 에서는 빈 목록 — 재발급과 같은 모델) | PENDING 없음 404, 코드 불일치 400 `MFA_INVALID_CODE` |
| `POST /user/mfa/recovery-codes` (커밋 7) | `{code}` (TOTP) | `MfaRecoveryCodesModel{recoveryCodes}` — 이전 코드 전부 삭제 | 꺼져 있음 409, 코드 불일치 400 |
| `POST /user/mfa/disable` | `{method: totp\|recovery, code}` | 204 | 꺼져 있음 409, 코드 불일치 400 |

- setup 은 기존 PENDING 행을 새 시크릿으로 덮는다. 시크릿은 20바이트 `SecureRandom`.
- activate 성공 시: `status=ACTIVE`, `activated_at`, `last_used_step` 을 맞은 구간으로, **현재 세션을 뺀 나머지 세션을 폐기**(`UserSessionRevocationBizService.revokeAll`, 사유 `MFA_ENABLED`). 커밋 7 부터는 남아 있던 복구 코드 행을 지우고 새로 10개를 만든다.
- disable: credential·복구 코드 행 삭제.
- 재인증은 비밀번호가 아니라 현재 2단계 코드로 한다 — 소셜 전용 사용자는 `password_hash` 가 NULL 이다.
- 관리 API 의 코드 검증도 §5.2 재사용 방지를 거친다. 실패는 로그인 잠금 카운터와 별개인 `mfa:manage:attempt:{userId}` 를 올리고(Lua: INCR + 첫 값일 때 EXPIRE `manageLockSeconds`), `manageMaxFailures` 이상이면 TTL 이 끝날 때까지 코드를 보기 전에 429 `MFA_TOO_MANY_ATTEMPTS`. 성공하면 키를 지운다.

### 5.1a 등록 변경의 직렬화

- setup·activate·disable·복구 코드 재발급·관리자 초기화는 시작할 때 `UserMfaEntityService.lockCredential(userId)`(`SELECT … FOR UPDATE`)로 행을 잡고 **잠근 뒤의 상태**로 판단한다 — activate 가 커밋하기 전에 들어온 setup 은 기다렸다가 ACTIVE 를 보고 409 다.
- 로그인 관문의 활성 판정은 `isActiveForLogin`(`SELECT … FOR SHARE`)이고, 관문 `afterFirstFactor` 는 쓰기 트랜잭션이다 — 판정과 세션 발급이 한 트랜잭션이라, 로그인이 먼저 잡으면 활성화는 그 세션까지 폐기하고 활성화가 먼저면 로그인은 challenge 를 받는다.

### 5.2 코드 검증 (`MfaBizService.verify(userId, method, code): Boolean`)

- TOTP: credential 이 ACTIVE(activate 는 PENDING)인지 → `Totp.matchStep` → 일치 구간 `s` 로
  `UPDATE user_mfa_credentials SET last_used_step = :s WHERE user_id = :id AND (last_used_step IS NULL OR last_used_step < :s)` — 갱신 1행일 때만 통과.
- 복구 코드(커밋 7): 입력을 대문자·하이픈 제거로 정규화 → `TokenHasher.hash` →
  `UPDATE user_mfa_recovery_codes SET used_at = now WHERE user_id = :id AND code_hash = :h AND used_at IS NULL` — 갱신 1행일 때만 통과.
- 두 UPDATE 는 `@Modifying` JPQL 이고 `UserMfaJpaEntityService` 의 `@Transactional(transactionManager = "authTransactionManager")` 메서드에서 실행한다.
- 복구 코드 형식: Base32 8자를 `XXXX-XXXX` 로. 생성은 `SecureRandom` 5바이트.

### 5.3 challenge (API·브라우저 공통, 커밋 6)

`service/mfa/MfaChallengeBizService.kt` — 대기 상태의 유일한 저장소다. 브라우저도 HttpSession 에 대기 객체를 두지 않는다.

- `issue(user: UserDto, origin: MfaOrigin, provider: SocialProvider?, deviceType, deviceInfo, ipAddress): MfaChallengeDto(token, expiresIn, methods)`
  - 토큰: 32바이트 `SecureRandom` base64url. Redis 해시 `mfa:challenge:{sha256(token)}`, 필드 `userId, loginId, origin, provider, deviceType, deviceInfo, ipAddress, failures=0`, TTL `challengeTtlSeconds`.
  - `MfaOrigin`(`enums/auth/`): `API_PASSWORD`·`API_SOCIAL`·`AUTHORIZE`·`SOCIAL_BROWSER`. `provider` 는 소셜 출처에서만 채운다.
  - `methods` = `["totp"]`, 커밋 7 부터 남은 복구 코드가 있으면 `"recovery"` 추가.
- `complete(token, allowedOrigins: Set<MfaOrigin>, method, code, ipAddress): MfaCompletionDto` — 순서:
  1. 해시 조회. 없으면(만료·소비·삭제) 401 `MFA_CHALLENGE_INVALID`.
  2. `origin ∉ allowedOrigins` 면 401 `MFA_CHALLENGE_INVALID` — challenge 는 그대로 두고 코드도 보지 않는다(다른 경로로 쓰지 못할 뿐 소비되지 않는다).
  3. `isIpBlocked(ip)` 403, `isUserLocked(loginId)` 423 — 코드를 보기 전(불변식 6).
  4. `MfaBizService.verify`. 불일치면 Lua `FAIL_SCRIPT`(키가 있을 때만 `HINCRBY failures 1`, 값이 한도 이상이면 `DEL`; 키가 없으면 아무것도 만들지 않고 -1). **-1 이면 실패로 세지 않고 401 `MFA_CHALLENGE_INVALID`** — 동시에 낸 다른 요청이 이미 통과한 경우다. 아니면 `recordFailedAttempt(loginId, ip)` → `MFA_CHALLENGE_FAILURE` 감사 → 400 `MFA_INVALID_CODE`(잠기면 423).
  5. 일치면 `DEL` — 반환 1 일 때만 계속(동시 성공 경쟁에서 하나만, 불변식 4). 0 이면 트랜잭션을 롤백 전용으로 표시해 방금 한 사용 표시(복구 코드·TOTP 구간)를 되돌리고 401 `MFA_CHALLENGE_INVALID`.
  6. `clearAttempts(loginId, ip)` → `SessionIssueBizService.issue` → 성공 감사: `API_PASSWORD`·`AUTHORIZE` 는 `logLoginSuccess(sessionId)`, `API_SOCIAL`·`SOCIAL_BROWSER` 는 `logSocialLoginSuccess(provider, sessionId)`(지금 소셜 성공 감사와 같은 기록). 이어서 `MFA_CHALLENGE_SUCCESS`(복구 코드면 `MFA_RECOVERY_CODE_USED`).
  - 반환 `MfaCompletionDto(origin: MfaOrigin, session: IssuedSessionDto)`. 6단계의 카운터 정리·발급·성공 감사는 `LoginCompletionBizService.complete(user, provider, …, clearAttempts = true)` 가 한다.
- 호출자별 `allowedOrigins`: `POST /auth/login/mfa` 는 `{API_PASSWORD, API_SOCIAL}`, `POST /auth/mfa`(브라우저)는 `{AUTHORIZE, SOCIAL_BROWSER}`.
- 실패 감사·카운터는 `noRollbackFor` 로 커밋되게 한다(`AuthBizService.login` 과 같은 이유).

### 5.4 1단계 출구 (커밋 6 — 네 경로를 한 커밋에서 모두 막는다)

- 공통: 1단계 출구는 모두 관문 `MfaChallengeBizService.afterFirstFactor(user, origin, provider, device…, ip)` 만 부른다. 2차 인증이 ACTIVE 면 challenge, 아니면 인증 완료 지점 `service/auth/LoginCompletionBizService.complete(user, provider, …, clearAttempts = !origin.isSocial)`(카운터 정리 → `SessionIssueBizService.issue` → 성공 감사: provider 가 있으면 `logSocialLoginSuccess`, 없으면 `logLoginSuccess`). 새 로그인 경로도 이 관문을 지나면 2차 인증을 빠뜨리지 않는다 (근거: 리뷰_이력.md 「/simplify 반영」).
- BizService 는 `sealed interface LoginOutcomeDto { data class Tokens(val session: IssuedSessionDto); data class MfaRequired(val challenge: MfaChallengeDto) }` 를 돌려준다(`dto/auth/`, sealed 계층이라 한 파일).
- MappingService 는 경로 종류별로 다른 Model 을 컨트롤러에 준다(`model/auth/`, 각각 sealed 계층 한 파일).
  - API(`AuthMappingService.login`·`SocialAuthMappingService.socialLogin`): `sealed interface LoginOutcomeModel { Tokens(TokenResponseModel) ; MfaRequired(MfaChallengeModel) }`. `MfaChallengeModel{mfaToken, expiresIn, methods}`(1st-party 응답 규칙대로 camelCase).
  - 브라우저(`AuthMappingService.loginForBrowser`·`SocialAuthMappingService.socialLoginForBrowser`): `sealed interface BrowserLoginOutcomeModel { SignedIn(BrowserPrincipalModel) ; MfaRequired(mfaToken: String) }`. `SignedIn` 은 지금 반환값(`BrowserPrincipalModel`)을 그대로 감싸 `BrowserSessionAuthenticator.signIn` 에 넘긴다. 소셜 `SignedIn` 은 지금처럼 매핑 서비스가 토큰 인계까지 끝낸 뒤 돌려준다.
- 1단계 시작 출처: `AuthBizService.login` → `API_PASSWORD`, `loginForBrowser` → `AUTHORIZE`, 네이티브 소셜 → `API_SOCIAL`, 소셜 콜백 → `SOCIAL_BROWSER`.

| 경로 | MfaRequired 일 때 | Tokens 일 때 |
|---|---|---|
| `POST /auth/login` | 202 `MfaChallengeModel` | 200 `TokenResponseModel`(지금과 같음) |
| 네이티브 `POST /auth/oauth2/{p}/login` | 202 `MfaChallengeModel` | 200(지금과 같음) |
| `POST /oauth2/login` | `MfaPendingTokenStore.begin(request, token)`(토큰 저장 + `changeSessionId`) → `302 /auth/mfa` | 지금과 같음 |
| 소셜 브라우저 콜백 | 같은 방식으로 `302 /auth/mfa` | 지금과 같음 |

- `POST /auth/login/mfa` (API 체인 permitAll): `{mfaToken, method, code}` → `AuthMappingService.completeMfa` → `complete(token, {API_PASSWORD, API_SOCIAL}, …)` → 200 `TokenResponseModel`(`MfaCompletionDto.session.tokens`).
- `config/security/browser/MfaPendingTokenStore.kt` — 요청 경계 보조(`AuthorizationRequestStore` 와 같은 자리). HttpSession 속성 `MFA_PENDING_TOKEN` 에 **문자열 토큰만** 둔다(세션에는 SecurityContext·CSRF·문자열만, 규약 9-3). `begin`(저장과 세션 ID 교체를 함께), `peek`, `clear`.

### 5.5 브라우저 2단계 화면 (커밋 6)

- `controller/auth/BrowserMfaController.kt`(`@Controller`) → `BrowserMfaMappingService` → `MfaChallengeBizService`·`AuthBizService`·`TokenHandoffBizService`.
  - 주입 허용 목록 안에 있다: MappingService, 요청 경계 보조(`MfaPendingTokenStore`·`BrowserSessionAuthenticator`·`AuthorizationRequestStore`·`ClientIpResolver`).
- `GET /auth/mfa` → `MfaPendingTokenStore.peek` 이 없으면 `/oauth2/login?expired`. 있으면 `BrowserMfaMappingService.pendingView(token)` 이 challenge 존재를 확인하고(없으면 토큰을 지우고 `/oauth2/login?expired`) `templates/auth/mfa.html` 을 보여 준다. 복구 코드 전환은 커밋 7.
- `POST /auth/mfa` (CSRF 필수) `method, code` → `BrowserMfaMappingService.complete(token, method, code, ip): BrowserMfaResultModel`.
  - 결과 `BrowserMfaResultModel{principal: BrowserPrincipalModel, origin: MfaOrigin}` — 매핑 서비스가 `complete(token, {AUTHORIZE, SOCIAL_BROWSER}, …)` → `AuthBizService.browserPrincipalOf(MfaCompletionDto.session)`(발급 결과의 세션 ID 로 조회 — 토큰을 다시 검증하지 않는다)을 하고, `MfaCompletionDto.origin` 이 `SOCIAL_BROWSER` 면 `TokenHandoffBizService.put(session.sessionId, session.tokens)` 까지 끝낸다. 출처 검사는 `complete` 2단계에서 코드 소비·세션 발급 전에 끝난다.
  - 컨트롤러: 성공이면 `MfaPendingTokenStore.clear` → `BrowserSessionAuthenticator.signIn(principal)` → origin 이 `AUTHORIZE` 면 `AuthorizationRequestStore.take`(없으면 `/oauth2/login?success`), `SOCIAL_BROWSER` 면 `/demo/auth/callback`.
  - 실패: `MFA_INVALID_CODE` 면 같은 화면에 메시지. `MFA_CHALLENGE_INVALID`·423·403 이면 토큰을 지우고 `/oauth2/login?error`.
- `/auth/mfa` 를 `BrowserSecurityPaths.PATHS` 에 추가하고 브라우저 체인에서 `permitAll` 로 둔다(진행 근거는 세션의 토큰과 Redis challenge 뿐이다).

### 5.6 관리자 초기화 (커밋 8)

- `DELETE /admin/security/accounts/{userId}/mfa` — `AdminSecurityController`, `hasPermission(null,'admin:security:manage')` → `SecurityMappingService.resetMfa` → `MfaBizService.resetByAdmin(userId, adminId)`(세션 폐기는 `UserSessionRevocationBizService.revokeAll(userId, MFA_RESET_BY_ADMIN, null)`).
- credential·복구 코드 삭제, 그 사용자의 세션 전부 폐기(사유 `MFA_RESET_BY_ADMIN`), `mfa:manage:attempt:{userId}` 삭제. 대상 없음 404.

### 5.7 감사

`AuditEventType` 에 추가: `MFA_ENROLLED`, `MFA_DISABLED`, `MFA_RESET_BY_ADMIN`, `MFA_CHALLENGE_SUCCESS`, `MFA_CHALLENGE_FAILURE`, `MFA_RECOVERY_CODE_USED`, `MFA_RECOVERY_CODES_REGENERATED`. DDL 변경 없음(`event_type VARCHAR(50)`).

## 10. 롤백 기준

- 커밋 단위가 기능 단위라 `git revert` 하나가 기능 하나의 **코드**를 되돌린다. 커밋 6~8 은 뒤에서부터 되돌린다.
- Flyway 파일은 되돌리지 않는다(적용된 마이그레이션은 지우거나 고치지 않는다). 커밋 5·6 을 되돌릴 때는 `git revert --no-commit <커밋>` → `git checkout <커밋> -- src/main/resources/db/migration/auth/ddl/V4__add_auth_time.sql`(커밋 6 은 `V5__create_mfa_tables.sql`) → 커밋. V4·V5 는 컬럼·테이블 추가뿐이라 코드만 되돌려도 기존 기능이 동작한다.

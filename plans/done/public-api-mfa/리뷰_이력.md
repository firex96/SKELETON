## 설계 근거

### 세션 발급을 먼저 하나로 모은다 (커밋 1)

같은 발급 순서가 `AuthBizService.createSessionAndTokens` 와 `SocialAuthBizService.createTokens` 에 따로 있다. 2단계 통과 지점이 넷(API 비밀번호·API 소셜·브라우저 인가·브라우저 소셜)으로 늘어나는데, 두 구현을 그대로 두면 2단계 뒤 발급이 경로마다 갈라진다. 동작 변화가 없는 리팩터를 먼저 별도 커밋으로 올린다(커밋 규율: 기능 구현에 리팩터가 선행하면 따로).

### 재사용 방지를 DB 조건부 UPDATE 로 한다

- Redis 에 마지막 구간을 두면 캐시 유실·만료 때 같은 코드가 다시 통과한다. DB 행의 `last_used_step` 을 `<` 조건으로 갱신하면 한 문장 안에서 원자적이고 영구적이다.
- asp-net-core 는 ASP.NET Core Identity 기본을 따르고 재사용 방지가 없다(같은 30초 구간 안에서 코드 재사용 가능). 개념 대조에서 이 점은 public-api 가 더 엄격하게 간다. 그 레포 처리는 설계서 §9 미결.

### 재인증은 비밀번호가 아니라 현재 2단계 코드로 한다

소셜 전용 사용자는 `password_hash` 가 NULL 이다. 비밀번호 재확인을 요구하면 그 사용자는 2차 인증을 끌 수도, 복구 코드를 다시 받을 수도 없다. 현재 TOTP·복구 코드를 요구하면 모든 사용자가 같은 규칙을 쓴다. asp-net-core 는 disable 에 비밀번호를 요구한다 — 그 레포는 소셜 전용 사용자도 비밀번호 없이 만들 수 있는지에 따라 다르며, 여기서는 따르지 않는다.

### 2단계 실패가 비밀번호 실패와 같은 잠금 카운터를 쓴다

challenge 마다 5회 한도만 두면, 비밀번호를 아는 공격자가 challenge 를 새로 받아 가며 무한히 시도할 수 있다. 계정 단위 카운터(`LoginAttemptBizService`)를 공유하면 challenge 를 갈아도 계정 잠금에 닿는다. asp-net-core 도 Identity 잠금 카운터를 2단계와 공유한다(5회, 30분).

### 소셜 잠금 수정(커밋 4)을 2차 인증보다 앞에 둔다

2단계 실패가 계정을 잠그는데, 소셜 경로가 잠금을 보지 않으면 잠긴 계정이 소셜 1단계로 다시 challenge 를 받는다. 잠금이 소셜에도 걸린 뒤에 2단계를 얹는다.

### `/user/password/change` 는 현재 세션을 남긴다

`/auth/password/change` 는 모든 세션을 폐기한다. 사용자 자기 관리 경로는 방금 비밀번호를 바꾼 기기에서 계속 쓰는 흐름이라 현재 세션을 남기고 나머지만 폐기한다 — 탈취된 다른 세션은 끊기고, 사용자는 다시 로그인하지 않아도 된다. 두 경로의 차이는 문서에 적는다.

### 브라우저 대기 상태는 Redis challenge, 세션에는 토큰 문자열만 (1라운드 번복)

- 처음 설계는 대기 객체(`MfaPendingModel`)를 HttpSession 속성에 두었다. Codex 1라운드가 짚었듯 Spring Session 은 요청마다 읽은 사본이라 동시 제출 두 건이 각자 속성을 보고 둘 다 성공할 수 있고, 레포 규약 9-3(세션에는 SecurityContext·CSRF·문자열만, 1회 소비 값은 Redis `GETDEL`)에도 어긋난다.
- 그래서 API·브라우저가 같은 Redis challenge(`MfaChallengeBizService`)를 쓰고, 브라우저 세션은 토큰 문자열만 든다. 소비는 `DEL` 반환값 하나로 판정하므로 경로와 무관하게 한 번이다. 만료·잠금 확인도 한 곳(`complete`)에 있어 GET/POST 어느 쪽으로 들어와도 같은 규칙을 지난다.
- 세션 쿠키를 새로 만들지 않고, 1단계 뒤 `changeSessionId` 로 세션 고정을 막는 점은 그대로다. SecurityContext 는 2단계 뒤에만 만든다(불변식 1).

### 모든 로그인 경로의 2단계를 한 커밋에 둔다 (1라운드 번복)

처음에는 비밀번호·인가 서버·소셜을 커밋 6·7·8 로 나눴다. 그러면 커밋 6 시점에 사용자가 2차 인증을 켜도 소셜 경로로 세션을 받을 수 있어, 중간 커밋이 불변식 1 을 어긴다(Codex 1라운드). "2차 인증을 켠 계정은 어느 경로로도 2단계 없이 세션을 받지 않는다" 가 기능의 완결 조건이므로 네 경로를 커밋 6 하나에 묶는다. 커밋 수는 10 → 8.

### 1단계 성공은 실패 카운터를 지우지 않는다 (1라운드 반영)

`verifyPassword` 가 성공 시 `clearAttempts` 를 하면, 비밀번호를 아는 공격자가 2단계를 몇 번 틀린 뒤 비밀번호로 다시 들어와 누적을 지울 수 있다. 초기화는 최종 성공 지점(2차 인증이 없으면 1단계 직후, 있으면 2단계 성공 뒤)으로 옮긴다.

### `auth_time` 은 세션 ID 로 조회한다 (1라운드 반영)

3rd-party 클라이언트의 코드는 authorize 가 아니라 `consent` 에서 만든다. 두 경로 모두 브라우저 principal 의 세션 ID 를 넘기고, 코드 발급 지점이 `validateSession(sessionId).authenticatedAt` 을 읽는다. principal(`AuthenticatedUser`)에 필드를 더하는 방법은 쓰지 않았다 — Spring Session 이 JDK 직렬화로 저장한 기존 브라우저 세션의 형식이 바뀌어 배포 직후 역직렬화가 깨진다.

### 로컬 암호화 키는 환경변수 (1라운드 반영)

설정값·비밀값 규약의 yml 예외는 `local` 프로필의 docker compose 계정뿐이다. `jwt-secret` 이 `application-local.yml` 에 값으로 있는 것은 기존 상태이고, 새 비밀을 같은 방식으로 늘리지 않는다. 고정 값은 테스트 소스셋(`application-testcontainers.yml`·`application-e2e.yml`)에만 둔다.

### 관리 API 시도 제한은 로그인 잠금과 분리 (1라운드 Minor 반영)

관리 API 는 이미 인증된 세션에서 오므로 로그인 잠금을 걸면 탈취자가 피해자 계정을 잠글 수 있다. 대신 사용자별 별도 카운터(5회/15분, 429)로 세션 탈취 뒤의 코드 추측만 막는다.

### `auth_time` 원천은 `user_sessions.created_at`

2차 인증이 들어오면 세션은 2단계 통과 시점에 만들어진다(불변식 1). 그래서 세션 생성 시각이 곧 인증 완료 시각이다. access 토큰 재발급은 `access_token_issued_at` 만 바꾸므로 `created_at` 은 원래 인증 시각을 유지한다.

## 구현 노트 (설계와 다르게 한 것과 그 이유)

### 커밋 5 — `oauth2_refresh_tokens.auth_time` 컬럼을 두지 않았다

설계 §4.3·§6 은 V4 에서 인가 코드와 refresh 토큰 두 테이블에 `auth_time` 을 더하고, refresh grant 의 id_token 도 그 값을 쓰게 했다. 구현하면서 확인해 보니 refresh grant(`OAuth2AuthorizationBizService.refreshAccessToken` → `issueAccessToken`)는 **id_token 을 발급하지 않는다**. 그래서 refresh 토큰 쪽 컬럼은 읽는 곳이 없다. V4 는 `oauth2_authorization_codes.auth_time` 하나만 더한다. 검출 테스트의 "refresh grant 뒤에도 같은 값" 항목도 해당하지 않아 뺐다. refresh grant 가 id_token 을 내게 바뀌면 그때 컬럼을 더한다(새 마이그레이션).

### 커밋 6 — 이름·응답 키·설정 등록을 주변 코드에 맞췄다

- **엔티티·리포지토리·엔티티 서비스 이름**: 설계는 `UserMfaCredentialJpaEntity`·`…JpaRepository`·`UserMfaJpaEntityService`·`MfaStatus`(`StringEnum` + 변환기)였다. public-api 의 auth 모듈은 전부 `~Entity`·`~Repository`·`~EntityService` 와 일반 enum(`@Enumerated(STRING)`, 예: `UserStatus`)을 쓴다. 한 패키지 안에서 두 규칙이 섞이지 않게 auth 모듈 쪽에 맞췄다: `UserMfaCredentialEntity`·`UserMfaRecoveryCodeEntity`·`UserMfaCredentialRepository`·`UserMfaRecoveryCodeRepository`·`UserMfaEntityService`·`MfaStatus`(일반 enum). 요청 값 `method` 는 JSON 값이 소문자(`totp`)라 `MfaMethod` 만 `StringEnum` 이다.
- **응답 키**: 설계 표기는 `mfa_token`·`recovery_codes_left`·`otpauth_uri` 였다. 1st-party API 응답은 모두 camelCase(`accessToken`·`expiresIn`)라 `mfaToken`·`expiresIn`·`recoveryCodesLeft`·`otpauthUri`·`recoveryCodes` 로 맞췄다.
- **`MfaProperties` 등록 위치**: 설계는 `SecurityConfiguration` 의 `@EnableConfigurationProperties` 였다. 그 클래스는 `@Profile("!test")` 라 test 프로필 컨텍스트에서 MFA 빈이 깨진다. 별도 `MfaConfiguration` 에서 등록한다.
- **`MfaActivatedModel` 변환**: 필드가 하나인 data class 는 MapStruct 가 `copy` 를 프로퍼티로 읽어 컴파일이 실패한다. 매핑 서비스가 직접 만든다.
- **`MfaMethod.RECOVERY`**: 커밋 6 에는 `TOTP` 만 두고 복구 코드 커밋(7)에서 더한다 — 커밋 6 시점에 받을 수 없는 값을 API 가 받지 않게.
- **벌크 UPDATE 와 영속성 컨텍스트**: 조건부 UPDATE 에 `flushAutomatically`·`clearAutomatically` 를 켰다. 같은 트랜잭션에서 읽어 둔 엔티티를 고치면(activate) 낡은 `last_used_step` 이 덮어쓸 수 있기 때문이다.

### 커밋 7 — 복구 코드 유일성을 사용자 단위로

설계는 `code_hash` 단독 UNIQUE 였다. 복구 코드는 Base32 8자(40비트)라 사용자 전체에서 해시가 겹칠 수 있다 — 약 100만 개면 충돌 확률이 절반에 가깝고, 그때 단독 UNIQUE 는 엉뚱한 사용자의 활성화·재발급을 실패시킨다. 조회·사용은 항상 `user_id` 와 함께 하므로 유일성을 `(user_id, code_hash)` 로 둔다. 코드 길이를 늘리는 대안은 사람이 옮겨 적는 값이라 택하지 않았다(시도 제한·계정 잠금이 추측을 막는다).

V5 는 커밋 6 이 만든 파일이다. 아직 어디에도 적용되지 않은 새 마이그레이션이라 파일을 고치고, 커밋을 만들 때 커밋 6 시점 상태에 이 DDL 을 넣어 그 시점을 다시 검증한다(로컬 docker DB 는 옛 V5 체크섬 때문에 볼륨을 다시 만들었다 — 시드·테스트 데이터뿐).

### /simplify 반영 (커밋 8 시점 뒤, 2026-10-19)

재사용·단순화·효율·고도 네 관점을 돌렸다. 같은 지점을 가리키는 항목을 합쳐 동작·응답 계약을 바꾸지 않는 것만 반영했다.

| 반영 | 이유 |
|---|---|
| 1단계 출구 넷의 2차 인증 분기·성공 처리를 관문 `MfaChallengeBizService.afterFirstFactor` 와 인증 완료 지점 `LoginCompletionBizService.complete` 로 모았다 | 출구마다 `isEnabled` 를 기억해야 불변식 1 이 지켜지던 구조였다 — 파생 프로젝트가 새 로그인 경로를 더하며 분기를 빼먹으면 2차 인증이 우회된다. 카운터 정리 규칙(비밀번호 1단계 정리·소셜 1단계 미정리·2단계 정리)도 한 곳에 모였다 |
| 세션 일괄 폐기를 `UserSessionRevocationBizService.revokeAll` 하나로 내렸다 | `AuthBizService.revokeAllAndEvict`(private)의 사본이 비밀번호 변경·2차 인증 켜기·관리자 초기화에 복제돼 있었다. `AuthBizService` 를 그대로 주입하면 `MfaBizService` 와 순환이 생겨 별도 서비스로 뒀다 |
| challenge 토큰·키 해시를 `TokenHasher` 로 | 바이트 단위로 같은 계산을 다시 구현하고 있었다. Redis 키 형식은 같다 |
| challenge 저장을 Lua(HSET + EXPIRE) 한 번으로, 읽지 않는 필드(IP·실패 수 초기값)와 쓰지 않는 `MfaCompletionDto.provider` 삭제 | 두 호출 사이에 멈추면 TTL 없는 키가 남는다 |
| 잠금 예외 생성 `LoginAttemptBizService.accountLockedException` | 같은 문구가 네 곳에 있었다 |
| `MfaPendingTokenStore.begin` 이 토큰 저장과 `changeSessionId` 를 함께 | 세션 고정 방어가 호출자(두 컨트롤러)에 붙어 있어 새 진입점이 빠뜨리기 쉬웠다 |
| 200/202 분기 `LoginOutcomeModel.toResponseEntity()`(`controller/auth/support`) | 두 컨트롤러에 같은 분기 |
| `AuthBizService.browserPrincipalOf(IssuedSessionDto)`, `resolveBrowserPrincipal` 삭제 | 방금 발급한 세션으로 principal 을 만들며 JWT 를 다시 검증하고 있었다 |
| `SecurityBizService.resetMfa` 삭제(매핑 서비스가 `MfaBizService` 를 직접), `clearManageAttempts` private | 값을 더하지 않는 위임 |
| `MfaActivated*` 를 `MfaRecoveryCodes*` 로 합침 | 모양이 같은 DTO·Model 쌍. 응답 JSON 은 같고 OpenAPI 스키마 이름만 바뀐다 |

반영하지 않은 것: refresh 토큰 해시를 `TokenHasher` 로 합치기(저장 형식이 표준 Base64 → URL-safe 로 바뀐다), 공용 로그인 시도 카운터의 원자적 증가(기존 코드 — 후속 과제), authorize 의 세션 이중 조회·세션 ID 프로젝션 쿼리·credential 이중 조회(빈도가 낮고 범위 밖), `noRollbackFor` 통합·테스트 픽스처 통합(영향 작음).

또 하나: `docs/API_REFERENCE.md`·`docs/ERROR_CODES.md` 는 CRLF 인데 편집 도구가 LF 로 바꿔 파일 전체가 바뀐 diff 가 됐다. CRLF 로 되돌렸다. 커밋 시점 스냅샷도 CRLF 로 맞춰 다시 만든다.

### 검증 스크립트 — `build` 뒤 통합 테스트를 따로 돌린다

## asp-net-core 이관 — TOTP 재사용 방지

- 발견: asp-net-core 의 2단계(`Web/TwoFactorEndpoints.cs`)는 ASP.NET Core Identity 기본 검증을 쓰고, 마지막으로 통과한 TOTP 구간을 기록하지 않는다. 같은 코드를 그 구간(±허용 구간) 안에서 다시 내도 통과한다.
- 제안: 사용자별 마지막 사용 구간을 저장하고 `구간 > 마지막 구간` 일 때만 조건부 갱신으로 통과시킨다(public-api `UserMfaEntityService.markTotpStepUsed` 와 같은 방식). 동시에 같은 코드를 낸 요청 중 하나만 통과하는지 통합 테스트로 확인한다.
- 처리: 사용자 결정(2026-10-19)으로 asp-net-core 레포 작업 세션에 이관한다. 이 레포에서는 고치지 않는다.

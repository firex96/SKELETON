## 1. 목적

오류 응답 정리에서 남은 미결 네 건을 해결해 두 가지 상태를 만든다. 첫째, 모든 스켈레톤(Kotlin 3종 + asp-net-core)에서 **오류 응답의 HTTP 상태와 코드가 항상 일치**한다. 프레임워크가 정한 상태는 그대로 쓰고, 그 상태마다 코드가 있다. 둘째, **응답 문구가 사용자에게 그대로 보여도 되는** 문장이다. 아울러 클라이언트 연동 문서가 실제 서버와 맞게 한다.

|---|---|---|
| 1. asp 4xx 문구 | MVC 검증 응답 `errors` 에 .NET 기본 문구가 나간다(`The JSON value could not be converted to System.Decimal. ## 2. 사용자 결정 (2026-10-26)

- asp 결함은 **이번 작업에서 함께 고친다** — asp 작업은 그 레포에서 한다는 워크스페이스 원칙의 예외로, 이 작업에 한해 SKELETON 에서 계획·리뷰하고 asp 레포에서 커밋한다.
- 405·415 등은 **상태 기반 일괄 처리**. Spring `ErrorResponse` 예외는 그 HTTP 상태로 응답하고, 코드는 상태에서 고른다. 공통 코드를 새로 둔다.
- 범위 밖 개선 넷을 모두 한다(미결 3 의 셋 + 미결 4).
- 이 계획이 정한 것: asp 의 사용자 문장은 한국어다 — asp 업무 예외 문구가 이미 한국어(「코드가 맞지 않아요.」)이고 Kotlin `ErrorReason` 도 한국어다(근거: 리뷰_이력.md 「asp 문구 언어」).

## 3. 접근법

### 3.1 상태 기반 일괄 처리 (Kotlin public·internal)

- 새 공통 코드: `METHOD_NOT_ALLOWED_ERROR` 405 G017 `Method Not Allowed` · `NOT_ACCEPTABLE_ERROR` 406 G018 `Not Acceptable` · `PAYLOAD_TOO_LARGE_ERROR` 413 G019 `Payload Too Large` · `UNSUPPORTED_MEDIA_TYPE_ERROR` 415 G020 `Unsupported Media Type`. Kotlin 전용이던 `SERVICE_UNAVAILABLE_ERROR` 503 G016 `Service Unavailable` 은 asp 에도 두어 공통 코드로 옮긴다.
- `ErrorCode.fromStatus(status)`: 상태별 대표 코드를 명시한 목록에서 고른다(첫 일치가 아니다 — 400 은 `BAD_REQUEST_ERROR`, 404 는 `NOT_FOUND_ERROR`).
- 상태 범위 계약: 목록은 Spring 기본 `ErrorResponse` 예외가 내는 상태 전부(400·404·405·406·413·415·500·503)와 스켈레톤이 직접 쓰는 상태(401·403·409·423·502)를 덮는다. 그러면 프레임워크 상태는 항상 보존된다. 목록 밖 상태는 앱이 `ResponseStatusException` 등에 임의 상태를 줄 때만 생긴다. 그때는 4xx → `BAD_REQUEST_ERROR`(400), 5xx → `INTERNAL_SERVER_ERROR`(500)로 응답하고, HTTP 상태도 그 코드의 상태가 된다. 상태와 코드가 어긋난 응답은 어떤 경우에도 나가지 않는다. 업무 상태가 필요하면 코드를 추가한다(`CodedException`).
- 캐치올 핸들러: `ex is ErrorResponse` 이면 `fromStatus(ex.statusCode.value())` 의 코드로 응답한다(HTTP 상태 = 코드 상태 — 기존 `respond` 의 단일 출처 불변식 유지). 문장은 `ErrorReason` 에 상태별 고정 문장으로 둔다. 기존 전용 핸들러(404·바인딩·헤더 등)는 그대로 우선한다.

### 3.2 상태 기반 일괄 처리 (batch)

- batch 는 코드 체계가 달라 공통 코드표 대상이 아니다. 새 코드 `COMMON_003` 404 경로 없음 · `COMMON_004` 405 · `COMMON_005` 406 · `COMMON_006` 413 · `COMMON_007` 415 · `COMMON_008` 503 을 둔다(제목은 영문, 기존 batch 문구 관례). 기존 `INVALID_REQUEST`(400)·`INTERNAL_ERROR`(500)와 합쳐 Spring 기본 `ErrorResponse` 예외의 상태(400·404·405·406·413·415·500·503)를 모두 덮는다.
- `ErrorCode.fromStatus` 는 batch 일반 코드 목록에서만 고른다(404 가 `JOB_NOT_FOUND` 로 가지 않게). 상태 범위 계약은 3.1 과 같다 — 목록 밖 상태는 `INVALID_REQUEST`(400)·`INTERNAL_ERROR`(500)이고 HTTP 상태도 따라간다.
- 타입 불일치(`MethodArgumentTypeMismatchException` — 상위 `TypeMismatchException` 은 변환기 부재 500 까지 덮으므로 쓰지 않는다)·본문 형식 오류(`HttpMessageNotReadableException`)는 400 `INVALID_REQUEST` 전용 핸들러. `details` 에 요청 값·예외 메시지를 싣지 않는다.

### 3.3 asp-net-core

- `ErrorCode.cs` 에 G016~G020 다섯 코드를 두고 `ByStatus` 에 넣는다 → `UseStatusCodePages` 가 만드는 405·406·413·415·503 응답의 코드가 상태와 맞는다.
- 상태 범위 계약은 3.1 과 같다. `ByStatus` 에 없는 상태의 ProblemDetails 는 대체 코드(400 `BadRequest` · 500 `InternalServerError`)를 붙이고, 응답 상태와 `status` 도 그 코드의 상태로 맞춘다(응답이 시작되기 전인 `CustomizeProblemDetails` 에서). 지금은 원래 상태에 400 코드를 붙여 어긋난다.
- `GlobalExceptionHandler`: `BadHttpRequestException` 은 그 `StatusCode` 로 `FromStatus` 의 코드와 고정 문장을 쓴다(지금은 500).
- MVC 검증 응답: 공통 웹 구성(`AddSkeletonWeb`)에서 세 곳을 정한다.
  - 모델 바인딩 문구(`ModelBindingMessageProvider`)를 한국어 사용자 문장으로.
  - DataAnnotations 기본 문구(메시지를 지정하지 않은 `[Required]`·`[StringLength]`·`[Range]` 등)를 한국어로.
  - 예외에서 온 모델 오류(JSON 입력 포매터)는 예외 메시지 대신 고정 문장으로.
- 열거형 바인더 문구에서 C# 타입 이름을 뺀다.
- Server 앱의 SPA 폴백(`MapFallbackToFile`)이 `/api/...` 의 잘못된 메서드 요청을 가로채는지 실행해 확인하고, 가로채면 API 경로가 405 를 받게 고친다.
- 최소 API(인증 엔드포인트)는 개발 환경에서 본문 형식 오류가 `BadHttpRequestException` 이 되므로 위 처리로 400 이 된다. 그 밖의 환경에서는 지금처럼 본문 없는 400 → `UseStatusCodePages` 가 채운다(내부 정보 없음).

### 3.4 범위 밖 개선

- (a) batch `convention/` 에 규약 테스트를 둔다: `src/main` 에서 `JobExplorer` 의 `getJobExecution(` 호출은 `util/JobExplorerExtensions.kt` 에서만 허용한다. BizService 자신의 `getJobExecution` 메서드와 구분하는 판정 방식은 ③ 에서 정한다.
- (b) public 에 `enums/AccessDenial.kt`(enum: 코드 + 문장 짝 — 인증 필요 401 · 권한 없음 403)을 둔다. `SecurityConfiguration` 의 진입점·거부 핸들러, `SecurityErrorResponseWriter`, `AccessDeniedException` 핸들러가 이것만 쓴다. `ErrorReason` 의 `UNAUTHORIZED`·`FORBIDDEN` 상수는 지운다(public·internal 같은 파일이라 둘 다).
- (c) `ErrorReason.forServerError`: 코드 상태가 502~504 이면 외부 서비스 문장, 그 밖의 5xx 는 일반 문장. 코드 이름 나열을 없앤다.

### 3.5 INTEGRATION_GUIDE 전면 교정 (public)

- 경로 접두 제거(서버는 context-path 없음, 포트 8080).
- 사용자 모델 `id`·nullable 필드·`groups`. 회원 가입 201 + 사용자 정보.
- 토큰 갱신은 access token 만 받고 기존 refresh token 을 유지한다. 401 재시도는 `/auth/login`·`/auth/refresh` 를 제외한다.
- 로그인 202 MFA 응답 → `/auth/login/mfa` 단계.
- 로그아웃 204 빈 본문(Swift 디코딩 오류 교정).
- 소셜 웹 흐름: `/auth/oauth2/{provider}/authorize` → 서버 콜백 → `/demo/auth/callback` → `POST /auth/session/token`(세션 쿠키 + CSRF). 토큰은 URL 에 실리지 않고, 브라우저 체인은 CORS 를 막아 같은 출처에서만 된다.
- 소셜 네이티브: `POST /auth/oauth2/{provider}/login {code}`(제공자 인가 코드). access token·ID token 로그인 예제는 백엔드가 지원하지 않으므로 지운다.
- `client_credentials` 예제의 없는 `GET /admin/users` 를 지우고, 그 토큰을 받는 자원 API 가 스켈레톤에 없음을 적는다(② 에서 확인).
- PKCE 예제: 서버는 모든 클라이언트에 시크릿을 요구한다(`OAuth2AuthorizationBizService.authenticateClient`, 공개 클라이언트 유형 없음). 그래서 인가 코드 교환을 시크릿을 보관하는 서버 측(백엔드) 예제로 바꾸고, 브라우저 단독 교환은 지원하지 않는다고 적는다.
- 문서 안의 정의 누락(`AuthApi`, `setTokens`·`fetchUser`)을 정리한다.
- 같은 결함: `docs/TROUBLESHOOTING.md`(curl 2곳), `docs/SECURITY_CHECKLIST.md`(속도 제한 예시 3곳), `CLAUDE.md`(Controller 예시 `@RequestMapping`).
- CRLF 문서(`INTEGRATION_GUIDE.md`)는 줄바꿈을 보존한다.

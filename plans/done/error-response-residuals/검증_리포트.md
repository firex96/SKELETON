## 6. 설계와 다르게 한 것

- 테스트 배치. Kotlin 프레임워크 상태 시나리오는 기존 `GlobalExceptionHandlerTest`·`TestExceptionController` 에 섞지 않고 새 `FrameworkStatusResponseIntegrationTest`·`TestFrameworkStatusController` 로 뒀다. batch 실제 경로 시나리오는 `JobExecutionNotFoundIntegrationTest` 대신 새 `RequestValueFormatIntegrationTest` 에 뒀다(클래스 이름이 다루는 내용과 맞게). 구현 설계·대응표를 같게 고쳤다.
- asp 상태 판정 테스트는 인증한 클라이언트로 보낸다. 앱이 인증을 기본으로 요구해(fallback 인가 정책) 익명 요청은 라우팅 판정(404·405·415)보다 먼저 401 이 된다 — 첫 실행에서 6건이 401 로 실패해 드러났다. 익명 401 은 `SpaFallbackTests` 에 한 건 둔다. README 「에러 응답」에 이 순서를 적었다.

## 6a. /simplify 와 재검증

판정 전문은 리뷰_이력.md 「/simplify 판정」. 반영한 것 가운데 동작이 바뀐 것은 하나다.

- `ErrorReason.forStatus` 에 401·403·409·423 문장을 더했다. 결함 — `ResponseStatusException(401)` 이 「잘못된 요청입니다.」를 싣던 것.
- 401·403 문장 값은 `ErrorReason` 상수 하나로 두고 `AccessDenial` 이 참조한다(값은 그대로).

나머지는 테스트 헬퍼 통합과 리터럴 상수화, `respond` 기본값이다.

재검증 범위: 공용 표면(`ErrorReason`·Kotlin 핸들러·asp 공통 웹)을 바꿨으므로 바뀐 레포 전체를 다시 돌렸다.

## 8. 구현 중 발견해 함께 고친 것

- `scripts/error-code-parity.sh` 는 같은 구분 코드가 「공통 코드」와 「스택 전용 코드」 예약 목록에 동시에 있어도 통과했다(음성 확인에서 발견, exit 0). 이번 작업이 G016 을 예약 목록에서 공통으로 옮기므로 같은 실수를 막는 검사 ⑦ 을 더했다. 실제 `RESULT: OK` exit 0, 음성(예약 목록에 G016 을 되돌린 사본 `ERROR_CODE_TABLE=<사본>`) exit 1 「공통 코드가 예약 목록에도 있다: G016」.

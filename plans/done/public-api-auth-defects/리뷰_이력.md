# public-api 인증 결함 수정 — 리뷰 이력

설계서([`구현_설계.md`](구현_설계.md))에 담긴 결정의 근거, 검토했지만 채택하지 않은 대안, 리뷰 라운드 기록을 둔다.

## 착수 전 결정 (2026-10-16, 사용자)

### 「쿠키 세션 범위」

- 결정: 브라우저 흐름에만 세션을 쓴다. 해당 흐름은 소셜 authorize·callback, `/oauth2/authorize`·`login`·`consent`, 토큰 교환이다. 일반 API 는 Bearer 를 유지한다.
- 채택하지 않은 대안: 브라우저 전체를 쿠키로 인증하는 방식. 토큰을 JS 에 전혀 노출하지 않는다는 장점이 있지만, 모든 변경 API 에 CSRF 를 적용해야 하고 API 인증 경로가 둘로 갈려 범위가 크게 넓어진다.
- 세션 하나가 세 결함을 함께 해결한다. state 를 브라우저에 묶을 곳(결함 1), 토큰을 쿼리 대신 넘길 통로(결함 2), 브라우저에서 로그인을 판정할 수단(결함 4)이 모두 이 세션이다.

### 「discovery 수정 방향」

- 결정: 광고를 실제 지원값에 맞춘다. 광고했지만 구현하지 않은 `client_secret_basic` 은 구현한다. userinfo 는 인가 서버 토큰을 받도록 고친다.
- 채택하지 않은 대안: 광고만 줄이는 방식. 이 경우 `userinfo_endpoint` 를 빼야 하는데, 그러면 OIDC 제공자로서 쓸모가 크게 줄어든다.

### 「파생 프로젝트 스윕 범위」

- 결정: 스켈레톤만 고친다. 파생 프로젝트 스윕·반영은 범위 밖이다(사용자 판단).

## 설계 근거

### 「SameSite=Lax」

- provider 콜백은 교차 사이트에서 오는 top-level GET 이다. `Strict` 로 두면 이 요청에 세션 쿠키가 실리지 않아 state 를 찾을 수 없다.
- `Lax` 는 교차 사이트 POST 에 쿠키를 싣지 않는다. 브라우저 체인의 변경 요청은 CSRF 토큰으로 별도로 보호한다.

### 「RedisSessionRepository(default) 사용」

- 통합 테스트의 Redis 는 클러스터 모드다(`application-testcontainers.yml`). 운영도 같은 구성을 가정한다.
- indexed 저장소는 keyspace 이벤트와 다중 키 연산에 기대므로 클러스터에서 문제가 생긴다.
- 이번 용도에는 principal 로 세션을 찾는 인덱스가 필요 없다. 세션 폐기는 `BrowserSessionValidationFilter` 가 요청마다 사용자 세션(`validateSession`)을 확인하는 방식으로 연동한다.

### 「1회용 토큰 교환(handoff)」

- 콜백 리다이렉트에서 토큰을 빼면, 페이지가 토큰을 받을 다른 통로가 필요하다. 세션에 60초 동안 보관했다가 CSRF 헤더가 있는 POST 로 한 번만 꺼내게 한다.
- 이렇게 하면 토큰이 URL, 브라우저 이력, Referer, 서버 접근 로그에 남지 않는다.

### 「authorize 의 redirect_to 제거」

- 로그인 뒤 돌아갈 곳을 쿼리로 받으면 오픈 리다이렉트 표면이 생긴다.
- 그래서 서버가 검증된 파라미터로 authorize URL 을 다시 조립해 세션에 저장한다. 저장 시점에 `/oauth2/authorize?` 접두사를 강제한다.

### 「브라우저 로그인이 AuthBizService.login 을 재사용」

- IP 차단, 계정 잠금, 실패 집계, 계정 열거 방지 메시지를 다시 구현하지 않기 위해서다.
- 사용자 세션 행이 만들어지므로 로그아웃과 전체 로그아웃이 브라우저 세션에도 그대로 걸린다.
- 발급된 토큰은 버린다.

### 「시크릿 없는 클라이언트 인증 = 인접 결함」

- `oauth2_clients.client_secret` 은 `NOT NULL` 이고, public 클라이언트 유형 컬럼이 없다.
- 그런데 `authenticateClient` 는 시크릿이 없으면 활성 클라이언트인지만 본다. 그래서 `client_id` 만 알면 `client_credentials`·`introspect`·`revoke` 를 부를 수 있다.
- discovery 의 `token_endpoint_auth_methods_supported` 를 바로잡는 일과 같은 코드라 이번 범위에 넣는다.

### 「OAuth2 오류 키 snake_case」

- RFC 6749 §5.2 는 `error_description`·`error_uri` 다. 기존 camelCase 는 표준 OAuth 클라이언트 라이브러리가 읽지 못한다.
- 오류 형식을 정리하는 결함 3 의 범위에서 프로토콜 형식을 RFC 와 일치시킨다.

### 「userinfo 가 1st-party 로그인 토큰을 거부」

- OIDC Core §5.3 의 userinfo 는 OAuth 2.0 access 토큰으로 보호되는 자원이다.
- 1st-party 로그인 토큰에는 scope 가 없어 claim 을 거를 근거가 없다. 그래서 받는 경로를 하나로 둔다.

#### 자체 정정 — Boot 4 Spring Session 키 이름

- 1라운드 제출본은 `spring.session.redis.*` 를 썼다. 이것은 Boot 4 에서 deprecated 키다.
- `spring-boot-session-data-redis-4.0.8.jar` 의 메타데이터로 확인해 `spring.session.data.redis.*` 로 고쳤다.

#### 자체 정정 — asp-net-core 형제 스윕 판정 오류

- 착수 전 스윕은 asp-net-core 의 OAuth 를 hit 0 으로 기록했다. 그런데 `email_verified` 를 추가로 스윕하다 `Web/OAuth/OAuthServerEndpoints.cs`(OpenIddict 인가 서버)를 발견했다.
- 이 레포에는 외부 로그인(`ExternalLoginEndpoints.cs`)과 SPA consent 페이지도 있다(커밋 `a683598`, `5b1b451`).
- 그래서 §2.1 의 asp-net-core 판정을 다시 스윕한 결과로 바꾼다.
- 재스윕은 워킹트리 기준으로 했다. 스윕 도중 HEAD 가 `ab0856f` 에서 `5ff613e` 로 바뀌었다(다른 세션의 커밋).
- 결과: 같은 결함 클래스 가운데 응답 형식 일부 이원화, `prompt_values` 과장, `email_verified` 고정 false 가 있다. 동의 화면은 그 레포의 진행 중인 작업이 연결하고 있다. 이 셋 모두 그 레포 소관으로 보류한다.
- 인접 발견: returnUrl 검증 `SafeLocalPath`·`safeReturnUrl` 이 `//`·`/\` 만 막는다. `/%09/evil.com` 처럼 탭으로 우회하면 오픈 리다이렉트가 될 가능성이 있다. public-api 는 이번 설계에서 `redirect_to` 쿼리를 없애므로 같은 표면이 없다.

## 구현 노트 (설계와 다르게 한 것과 그 이유)

### 기능 2

- **`/oauth2/authorize`·`/oauth2/login`·`/oauth2/consent` 를 브라우저 체인에 넣는 시점을 기능 4 로 옮겼다.** 설계 §5 기능 2 는 이 경로들을 기능 2 에서 넣게 했다. 그런데 브라우저 로그인 화면은 기능 4 에서 생긴다. 기능 2 에서 authorize 를 브라우저 체인으로 옮기면 Bearer 가 읽히지 않아 기존 `OAuth2AuthorizationE2ETest` 가 깨지고, 기능 2 커밋이 완결 상태가 되지 못한다. 그래서 기능 2 의 브라우저 체인 경로는 소셜 authorize·callback, `/auth/session/**`, `/demo/auth/callback` 이다. 기능 2 의 미인증 처리는 JSON 401 하나다.
- **브라우저 체인에서 CORS 를 껐다(`cors { disable }`).** Spring Security 는 `CorsConfigurationSource` 빈이 있으면 기본 `HttpSecurity` 에 CORS 를 적용한다. 지금 CORS 는 모든 출처를 credentials 와 함께 허용하므로, 쿠키를 싣는 경로를 교차 출처에 열지 않기 위해 끈다.
- **요청 캐시를 껐다(`requestCache { disable }`).** 세션 속성을 설계 §4.1 의 세 가지로 한정하기 위해서다. 기본값이면 미인증 접근 때 `SavedRequest` 가 세션에 쌓인다.
- 실제 서블릿 컨테이너는 `Location` 을 절대 URL 로 내보낸다. 통합 테스트는 출처를 떼고 비교한다.
- `SocialAuthE2ETest` 의 「소셜 로그인 URL 형식 검증」은 JSON `authorizationUrl` 대신 302 `Location` 을 단언하도록 바꿨다(엔드포인트 계약 변경에 따른 것).

### 기능 3

- 「쿠키가 없으면 401」 케이스는 「로그인하지 않은 세션은 CSRF 가 맞아도 401」 로 바꿨다. 쿠키가 없으면 세션이 없고 CSRF 토큰도 없으므로 CSRF 필터가 먼저 403 을 낸다. 401 은 세션은 있지만 로그인하지 않은 경우에만 관찰할 수 있다.
- `SocialProviderIdDiscoveryTest`(manual)와 `SocialLoginBrowserE2ETest`(browser) 도 authorize 가 302 로 바뀐 데 맞춰 고쳤다. 기본 실행 대상은 아니다.

### 기능 4

- **인접 결함(기능 3a)을 발견해 함께 고쳤다.** 전체 로그아웃 뒤 브라우저 세션이 살아 있는 e2e 실패를 추적하다 찾았다. 일괄 폐기가 폐기 뒤 "살아 있는 세션" 으로 캐시를 찾아, 폐기된 세션의 토큰이 캐시 만료(최대 1시간)까지 통과했다. 브라우저 세션뿐 아니라 API Bearer 토큰에도 해당하는 보안 결함이다. 설계서에 기능 3a 로 추가했다. 이 수정은 체크포인트 3 승인 뒤에 추가된 것이므로 ④ 리뷰 대상으로 명시한다.
- OAuth2 화면 템플릿(`templates/oauth2/`)은 데모 fragments 를 쓰지 않는다. README 「지워도 되는 샘플」에서 `templates/fragments/**` 를 지우면 실제 인가 흐름이 깨지지 않게 하기 위해서다.
- 데모 인덱스의 「OAuth2 동의」 카드(지운 고아 템플릿을 가리킴)는 `/oauth2/login` 으로 바꿨다.
- e2e 의 「쿠키 A·Bearer B」 케이스는 introspect 대신 `oauth2_authorization_codes.user_id` 로 확인한다. introspect 응답이 사용자 식별자를 보장하지 않기 때문이다.

#### 구현 노트 — id_token phone 클레임 제거 (기능 7)

- `SUPPORTED_SCOPES` 는 설계대로 phone 이 없다. 그런데 id_token 은 클라이언트가 phone scope 로 등록돼 있으면 `phone_number`·`phone_number_verified=false` 를 냈다. 광고하지 않는 scope 의 클레임을 내보내는 불일치라, 광고(scope·claims)와 출력이 일치하도록 id_token 의 phone 블록을 지웠다.

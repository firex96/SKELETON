# public-api 인증 결함 수정 — 구현 설계

- 대상 레포: `../spring-boot-public-api-skeleton` (Kotlin 2.3 / Spring Boot 4.1.1)
- 패키지 루트: `src/main/kotlin/com/rex/api/pub/skeleton/`. 아래 경로는 이 루트 기준이다.
- 테스트 루트: `src/test/{unit,integration,e2e}/kotlin/com/rex/api/pub/skeleton/`. 아래에서는 `…/` 로 줄인다.
- 작성일: 2026-10-16
- 근거와 결정 이유: [`리뷰_이력.md`](리뷰_이력.md)

## 1. 목적과 범위

파생 프로젝트에서 발견된 다음 결함을 원본 스켈레톤에서 고친다.

1. 소셜 로그인의 state 를 검증하지 않는다.
2. 소셜 콜백이 access 토큰과 refresh 토큰을 리다이렉트 쿼리스트링에 싣는다.
3. 403(과 401) 응답 본문의 형식이 경로마다 다르다.
4. 인가 서버의 로그인·동의 화면이 인가 흐름에 연결되어 있지 않다.
5. OIDC discovery 가 지원하지 않는 기능을 광고한다.

함께 고치는 인접 결함은 둘이다.
- 시크릿 없이 클라이언트 인증이 통과한다(기능 5).
- `email_verified` 가 실제 인증 여부와 무관하다(기능 6).

범위 밖:
- 형제 스켈레톤 코드(§2.1 스윕 결과 해당 없음)
- 기존 파생 프로젝트(§2.2 사용자 결정)

### 2.2 기존 파생 프로젝트

- 스윕하지 않는다. 사용자가 범위 밖으로 결정했다(2026-10-16, 결정자: 사용자).
- 이 변경은 기존 파생 프로젝트로 자동 전파되지 않는다. 바뀌는 외부 계약:
  - `GET /auth/oauth2/{provider}/authorize`: JSON 응답에서 302 로
  - 소셜 콜백: 쿼리 토큰에서 세션 교환으로
  - `GET`·`POST /oauth2/consent`: JSON 에서 HTML 폼으로
  - `/oauth2/authorize`: Bearer 인증에서 브라우저 세션 인증으로
  - 401·403 본문
  - OAuth2 오류의 키 이름
  - `/oauth2/userinfo` 가 받는 토큰
  - 시크릿 없는 클라이언트 인증 거부
  - 프로필의 `emailVerified` 의미

### 2.3 형제 공통 표면

- `docs/contract-surfaces.md` 「표면」표에는 `GlobalExceptionHandler`·`ErrorResponseModel`·`SecurityConfiguration` 이 없다(`grep` hit 0). 따라서 `sibling-diff.sh` 가 감시하는 공통 표면에 해당하지 않는다. `ErrorResponseModel` 의 형태는 바꾸지 않는다.

## 3. 오류 응답 계약 (전 기능 공통)

| 경로 | 401·403·400 응답 |
|---|---|
| OAuth2 프로토콜 엔드포인트 `/oauth2/token`·`introspect`·`revoke`·`userinfo` | JSON `OAuth2ErrorResponseModel` `{error, error_description, error_uri}` (RFC 6749 §5.2). `invalid_client` 는 `WWW-Authenticate: Basic realm="oauth2"`, userinfo 는 RFC 6750 §3 `WWW-Authenticate: Bearer …` 을 붙인다 |

| 브라우저 HTML 엔드포인트 `/oauth2/login`·`/oauth2/consent` 의 OAuth2 검증 오류 | 뷰 `oauth2/error`(HTML). 상태는 `invalid_client` 면 401, 그 외 400 이다. `Location` 은 없고 코드를 발급하지 않는다 |
| `/oauth2/consent` 미인증 접근 | `/oauth2/login` 으로 302 |
| 그 밖의 모든 경로(API 필터 체인 거부, 메서드 보안 거부, CSRF 거부, `/auth/session/**`, 업무 예외) | JSON `ErrorResponseModel` (`code`, `reason`, `errors`, `status`, `divisionCode`, `resultMessage`) |

## 4. 공통 기반 — 브라우저 세션 저장 계약

기능 2~4 가 공유한다.

### 4.1 세션에 두는 것

Spring Session Redis 는 JDK 직렬화를 쓴다. 세션에는 아래 세 가지만 둔다.

| 속성 | 타입 | 직렬화 |
|---|---|---|
| `SPRING_SECURITY_CONTEXT` | `SecurityContextImpl` → `UsernamePasswordAuthenticationToken(principal=AuthenticatedUser, authorities=SimpleGrantedAuthority…)` | `AuthenticatedUser` 에 `: java.io.Serializable` 과 `companion object { private const val serialVersionUID = 1L }` 를 추가한다. 나머지 타입은 Spring Security 가 이미 Serializable 이다. `groups`·`permissions` 는 `ArrayList(…)` 로 복사해 넣는다 |
| CSRF 토큰 | `DefaultCsrfToken` (`HttpSessionCsrfTokenRepository`) | Spring Security 가 Serializable 로 제공한다 |
| `PENDING_AUTHORIZATION_REQUEST` | `String` | 기본 Serializable |

토큰과 state 는 세션에 두지 않는다(§4.2).

### 4.2 1회 소비 값은 Redis 키 + `GETDEL`

- state 와 토큰 교환 값은 세션 속성이 아니라 독립 Redis 키에 둔다.
- 꺼낼 때는 `StringRedisTemplate.opsForValue().getAndDelete(key)` 를 쓴다. Redis 7 의 `GETDEL` 이 원자적이라 동시 요청 중 정확히 하나만 값을 얻는다. docker compose 와 Testcontainers 모두 `redis:7-alpine` 이다.
- 키는 단일 키이므로 클러스터 모드에서도 동작한다.
- 값은 JSON 이다(`JsonMapper`).

| 용도 | 키 | 값 | TTL |
|---|---|---|---|
| 소셜 state | `browser:social-state:{state}` | `{"browserSessionId": "...", "provider": "GOOGLE"}` | 300초 |
| 토큰 교환 | `browser:token-handoff:{userSessionId}` | `{"accessToken": "...", "refreshToken": "...", "expiresIn": 3600}` | 60초 |

- `browserSessionId` 는 Spring Session 의 세션 ID(`HttpSession.id`)다.
- `userSessionId` 는 로그인으로 만들어진 사용자 세션 ID(access 토큰 jti, `AuthenticatedUser.sessionId`)다.

### 4.3 설정과 의존성

- `build.gradle.kts` 에 `implementation("org.springframework.boot:spring-boot-starter-session-data-redis")` 를 추가한다.
- `application.yml` 에 다음을 둔다. Boot 4 키 이름이다(`spring-boot-session-data-redis` 4.0.8 메타데이터로 확인).

  | 키 | 값 |
  |---|---|
  | `spring.session.data.redis.repository-type` | `default` |
  | `spring.session.data.redis.namespace` | `skeleton:public-api:session` |
  | `spring.session.timeout` | `30m` |
  | `server.servlet.session.cookie.name` | `SKELETON_SESSION` |
  | `server.servlet.session.cookie.http-only` | `true` |
  | `server.servlet.session.cookie.same-site` | `lax` |
  | `server.servlet.session.cookie.secure` | `${browser-session-cookie-secure:true}` |

- `application-local.yml` 과 `src/test/integration/resources/application-testcontainers.yml` 에 `browser-session-cookie-secure: false` 를 둔다. 통합 테스트는 RANDOM_PORT HTTP 라 Secure 쿠키가 다음 요청에 실리지 않기 때문이다. e2e 는 `local,e2e` 프로필이라 `local` 값을 받는다.
- `.env.example` 의 「설정 (비밀 아님)」 블록에 `# BROWSER_SESSION_COOKIE_SECURE=true   # 브라우저 세션 쿠키 Secure (local 은 false)` 를 추가한다(`SecretKeyCoverageTest` 대상).
- README 「설정과 비밀값」 표에 같은 키를 추가한다.

### 4.4 필터 체인 분리

- `config/security/browser/BrowserSecurityPaths.kt` (`object`) 의 `PATHS` 가 브라우저 체인 경로의 정본이다. 값은 다음과 같다: `/auth/oauth2/*/authorize`, `/auth/oauth2/*/callback`, `/auth/session/**`, `/oauth2/authorize`, `/oauth2/login`, `/oauth2/consent`, `/demo/auth/callback`
- `SecurityConfiguration` 에 `browserSecurityFilterChain` 을 추가한다(`@Bean @Order(1)`).
  - `securityMatcher(*BrowserSecurityPaths.PATHS)`
  - `sessionCreationPolicy(IF_REQUIRED)`
  - CSRF 를 켜고 `HttpSessionCsrfTokenRepository` 를 쓴다.
  - `securityContext { it.securityContextRepository(HttpSessionSecurityContextRepository()) }`
  - `JwtAuthenticationFilter` 는 넣지 않는다.
  - 인가 규칙은 다음과 같다.

    | 경로 | 규칙 |
    |---|---|
    | `/auth/oauth2/*/authorize`, `/auth/oauth2/*/callback`, `/demo/auth/callback`, `/oauth2/authorize`, `/oauth2/login` | `permitAll` |
    | `/oauth2/consent`, `/auth/session/**` | `authenticated` |

  - 미인증 처리: `defaultAuthenticationEntryPointFor` 로 경로를 나눈다. `/auth/session/**` 는 `SecurityErrorResponseWriter` 401, 그 외는 `LoginUrlAuthenticationEntryPoint("/oauth2/login")` 이다.
  - `accessDeniedHandler` 는 기능 1 의 거부 핸들러(`ErrorResponseModel` 403)다.
- 기존 `securityFilterChain` 에는 `@Order(2)` 를 붙이고, permitAll·authenticated 목록에서 브라우저 경로를 지운다.
- **`JwtAuthenticationFilter` 의 서블릿 자동 등록을 끈다.** `@Component` 인 Filter 라 컨테이너 필터로도 돌기 때문이다.
  - `SecurityConfiguration` 에 `jwtAuthenticationFilterRegistration(filter): FilterRegistrationBean<JwtAuthenticationFilter>` 을 `isEnabled = false` 로 둔다. `securityAuditorContextFilterRegistration` 과 같은 방식이다.
  - 그 결과 JWT 인증은 API 체인 안에서만 일어난다.

## 5. 기능 단위 (= 커밋 단위, 이 순서로 구현한다)

각 기능에서 바뀐 계약은 같은 커밋에서 그 레포의 `CLAUDE.md`·`README.md`·`docs/` 에 반영한다.

### 기능 1 — 401·403 응답 형식을 §3 으로 통일한다

**만들 것**
- `config/security/SecurityErrorResponseWriter.kt` (`@Component`)
  - `fun write(response: HttpServletResponse, errorCode: ErrorCode, reason: String?)`
  - status 는 `errorCode` 의 HTTP 상태, content-type 은 `application/json`, 본문은 `ErrorResponseModel.of(errorCode, reason)` 이다.

**바꿀 것**
- `config/security/SecurityConfiguration.kt`
  - 엔트리포인트: `write(response, UNAUTHORIZED_ERROR, "인증이 필요합니다")`
  - 거부 핸들러: `write(response, FORBIDDEN_ERROR, "접근 권한이 없습니다")`
  - 임시 Map 본문을 지운다.
- `handler/GlobalExceptionHandler.kt`
  - `handleAccessDeniedException`: 인증이 null 이거나 `AnonymousAuthenticationToken` 이면 401 `UNAUTHORIZED_ERROR`, 그 외는 403 `FORBIDDEN_ERROR` 다.
  - `@ExceptionHandler(AuthorizationException::class)` 를 추가한다(`exception/auth/AuthorizationException`). 403 `FORBIDDEN_ERROR` 다.
- `model/oauth2/OAuth2ErrorResponseModel.kt`: `@field:JsonProperty("error_description")`, `@field:JsonProperty("error_uri")`
- `src/test/unit/…/convention/DeclarationStyleConventionTest.kt`: `SNAKE_CASE_CONTRACT` 에 `"OAuth2ErrorResponseModel"` 을 추가한다(D-4 — 프로퍼티명과 JSON 이름이 다른 Model 은 등록해야 한다).

**테스트**
- `src/test/e2e/…/security/ErrorResponseFormatE2ETest.kt` (신규, 실제 `SecurityConfiguration`)
  - ADMIN 그룹이 없는 사용자의 `/admin/**` URL 거부와, ADMIN 사용자의 `SUPER_ADMIN` 전용 `@PreAuthorize` 거부를 비교한다. 둘 다 403 이고, 본문 키 집합이 같고, `code=FORBIDDEN_ERROR`·`divisionCode=G008` 이어야 한다.
  - 토큰 없이 인증 필요 API 를 부르면 401 `code=UNAUTHORIZED_ERROR` 다.
- `src/test/unit/…/handler/GlobalExceptionHandlerTest.kt` (있으면 추가, 없으면 신규)
  - `AuthorizationException` 은 403 이다.
  - 익명 인증 상태의 `AccessDeniedException` 은 401 이다.
- `OAuth2AuthorizationE2ETest`·`OAuth2AuthorizationControllerTest` 의 오류 본문 단언은 `error_description` 키로 바꾼다.

**문서**
- `CLAUDE.md` 「5. Exception Handling」에 §3 표를 둔다.
- `docs/ERROR_CODES.md`: `resultMsg` 를 `resultMessage` 로, OAuth2 키를 snake_case 로, Security 핸들러도 `ErrorResponseModel` 을 쓴다고 적는다.

### 기능 2 — 브라우저 세션 체인과 소셜 state 검증

§4 의 기반 전체(의존성·설정·체인 분리·JWT 필터 등록 해제·`AuthenticatedUser` 직렬화)를 이 기능에서 도입한다.

**만들 것**
- `service/auth/SocialAuthorizationStateBizService.kt` (`@Service`, `StringRedisTemplate`·`JsonMapper` 주입)
  - `fun issue(browserSessionId: String, provider: SocialProvider): String`: `SecureRandom` 32바이트를 base64url(패딩 없음)로 만들어 `browser:social-state:{state}` 에 TTL 300초로 저장하고 state 를 돌려준다.
  - `fun consume(browserSessionId: String, provider: SocialProvider, state: String?): Boolean`
    - state 가 null 이거나 비면 false 다.
    - `getAndDelete("browser:social-state:$state")` 결과가 null 이면 false 다.

### 기능 3a — 일괄 세션 폐기가 폐기한 세션의 캐시를 지운다 (구현 중 발견한 인접 결함, 기능 4 선행)

- 결함: `AuthBizService.logoutAllSessions`·`changePassword` 는 DB 에서 일괄 폐기한 **뒤** `SessionCacheBizService.deleteAllUserSessions` 를 부른다. 이 함수는 "폐기되지 않은 세션" 을 조회해 캐시를 지우므로, 방금 폐기한 세션의 캐시(`session:{id}`)가 남고 그 토큰이 캐시 만료(액세스 토큰 만료)까지 통과한다. 기능 4 의 "전체 로그아웃이 브라우저 세션에도 걸린다" 계약이 이 결함 때문에 성립하지 않는다.
- 수정: `AuthBizService.revokeAllAndEvict(userId, reason, excludeSessionId)` (private)
  - 폐기 **전에** 대상 세션 ID 를 모으고 `UserSessionEntityService.revokeAll(ids)`(`WHERE session_id IN …`)로 **그 ID 만** 폐기한다.
  - `SessionCacheBizService.evictRevokedSessions(ids, userId)` — 트랜잭션이면 **커밋 뒤에**, 폐기 표식 `session:revoked:{id}`(TTL 5분)을 **먼저** 쓰고 세션 캐시·권한 캐시를 지운다. 단건 폐기(`invalidateSession`, `AuthBizService.logout`·`UserSelfBizService` 4곳)도 같은 규칙이다.
  - `SessionCacheBizService.getSession` 은 캐시 miss 로 DB 에서 읽은 값을 `cacheSessionUnlessRevoked` 로 쓴다 — 폐기 표식이 없을 때만 쓰는 Lua 스크립트(원자적)이고, 표식이 있으면 쓰지 않고 null 을 돌려준다. 두 키는 해시 태그를 공유한다: `session:{sessionId}`, `session:revoked:{sessionId}`(Redis 클러스터 같은 슬롯).
  - 사용자 단위 bulk 폐기(`revokeAllByUserId`·`revokeAllByUserIdExcept`)는 삭제한다.
- 테스트: `SessionOwnershipE2ETest` O-4(전체 로그아웃 뒤 다른 세션 토큰 401, 요청 세션 200)·O-5(비밀번호 변경 뒤 모든 세션 401). 수정 전 코드에서 둘 다 실패함을 확인했다.
- 스윕: `rg -e deleteAllUserSessions -e revokeAllByUserId -e revokeAllByUserIdExcept` (public `src/main/kotlin`) — `AuthBizService` 2곳 반영, `UserGroupBizService` 6곳은 폐기가 아니라 권한 갱신(세션이 살아 있어 조회에 잡힌다)이라 해당 없음, `UserSelfBizService` 의 폐기 4곳은 세션마다 `invalidateSession` 을 불러 해당 없음. 형제 internal·batch 는 hit 0(세션 표면 없음).

  - `POST /auth/logout-all`(Bearer) 로 사용자 세션을 폐기하면 같은 쿠키로 부른 다음 authorize 가 `/oauth2/login` 으로 간다.
  - 쿠키는 사용자 A, Bearer 는 사용자 B 로 authorize 를 부르면 코드는 A 로 발급된다(introspect 의 `sub` 로 확인).
  - **비리다이렉트 오류 보존**(기존 L628 계열을 HTML 계약으로 옮긴다)
    - `POST /oauth2/consent` 에 미등록 redirect_uri, 미등록 client_id, 허용되지 않은 scope, 잘못된 `code_challenge_method` 를 넣으면 400(미등록 client 는 401)이다.
    - 응답은 `text/html` 이고 `Location` 이 없으며, 해당 클라이언트의 코드 수가 늘지 않는다.
  - 기존 Bearer 기반 `/oauth2/authorize`·`consentPost` 호출은 `BrowserSession` 흐름으로 바꾼다. L388 의 405 주석 케이스는 지운다. 마커 `invalid_request`·`access_denied`·`refresh_token` 은 남긴다(§2.3).
- `src/test/integration/…/controller/oauth2/OAuth2AuthorizationControllerTest.kt`: JSON consent 케이스를 지우고 `OAuth2BrowserControllerTest` 로 옮긴다. 뷰 이름, 모델, 리다이렉트, 오류 뷰 상태를 단언한다.
- `src/test/unit/…/config/security/browser/AuthorizationRequestStoreTest.kt`: `/oauth2/authorize?` 가 아닌 URL 이면 예외, take 는 1회다.

### 기능 5 — 클라이언트 인증에 시크릿을 필수로 하고 `client_secret_basic` 을 구현한다

**만들 것**
- `config/security/ClientCredentials.kt`: `data class ClientCredentials(val clientId: String?, val clientSecret: String?)`
- `config/security/ClientCredentialsResolver.kt` (`@Component`)
  - `fun resolve(request: HttpServletRequest, formClientId: String?, formClientSecret: String?): ClientCredentials`
  - `Authorization: Basic` 이 있으면 base64 디코드 → 첫 `:` 로 분리 → 각각 `URLDecoder.decode(…, UTF_8)` 한다(RFC 6749 §2.3.1).
  - Basic 과 폼 `client_secret` 이 함께 오면 `OAuth2Exception(ERROR_INVALID_REQUEST)` 다.
  - Basic 형식이 깨졌으면(base64 오류, `:` 없음, 잘못된 % 인코딩) `OAuth2Exception(ERROR_INVALID_CLIENT)` 다.

**바꿀 것**
- scope 축소 규칙(RFC 6749 §3.3·§6): refresh_token grant 의 요청 scope 는 그 refresh token 의 승인 scope, client_credentials 의 요청 scope 는 클라이언트 등록 scope 의 부분집합이어야 한다. 넘으면 `invalid_scope`(400). userinfo 가 발급 기록의 scope 를 신뢰하므로 이 규칙이 그 전제다.
- `OAuth2AuthorizationBizService.authenticateClient`: `clientSecret` 이 비면 `OAuth2Exception(ERROR_INVALID_CLIENT, "클라이언트 인증이 필요합니다")` 다. 시크릿 없이 통과시키던 분기와 KDoc 의 public 클라이언트 서술을 지운다.
- `OAuth2AuthorizationController` 의 `token`·`introspect`·`revoke`: `HttpServletRequest` 를 받아 `clientCredentialsResolver.resolve(...)` 결과를 기존과 같이 `oAuth2AuthorizationMappingService.authenticateClient(clientId, clientSecret)` 에 넘긴다(컨트롤러는 BizService 를 직접 부르지 않는다). `ClientCredentialsResolver` 는 생성자로 주입한다(`config/` 요청 경계 보조).
- 같은 컨트롤러의 `@ExceptionHandler`: `invalid_client` 면 `WWW-Authenticate: Basic realm="oauth2"` 를 붙인다.

**테스트**
- `src/test/unit/…/config/security/ClientCredentialsResolverTest.kt`: Basic 정상, URL 인코딩된 `:` 를 포함한 시크릿, Basic 과 폼 동시 전송, 깨진 Basic
- `OAuth2AuthorizationE2ETest`
  - `client_secret_basic` 으로 `client_credentials` 가 성공한다.
  - `client_secret_post` 가 성공한다.
  - `client_id` 만 보내면 401 `invalid_client` 와 `WWW-Authenticate` 다.
  - 두 방식을 같이 쓰면 400 `invalid_request` 다.
  - L102 처럼 시크릿 없이 호출하던 기존 코드는 시크릿을 보내도록 고친다.
- `OAuth2AuthorizationControllerTest`: 시크릿 없는 호출을 고친다.

  - `SUPPORTED_SIGNING_ALGORITHMS = listOf("RS256")`
  - `SUPPORTED_CLAIMS` 는 기능 6 이후 userinfo 와 id_token 이 실제로 내보내는 claim 키의 합집합이다. 상수 목록으로 고정한다.

**테스트**

  - `response_types_supported` 의 각 값으로 authorize 가 `unsupported_response_type` 이 아니어야 하고, 광고하지 않은 `token` 은 그 오류여야 한다.

  - `claims_supported` 는 userinfo·id_token 출력 키의 상위집합이어야 하고, 각 광고 claim 은 둘 중 하나 이상에 나와야 한다.

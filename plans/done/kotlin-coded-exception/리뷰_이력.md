# Kotlin 스켈레톤 예외 구조 정리 — 리뷰 이력

설계서([`구현_설계.md`](구현_설계.md))에 담긴 결정의 근거, 검토했지만 채택하지 않은 대안, 리뷰 라운드 기록을 둔다.

## 발단

b2b(파생 프로젝트) academy·admin 모듈의 예외가 두 계열로 갈려 있었다. 공통 예외는 문자열 code 를 받지만 핸들러가 버리고, 전용 예외는 `ErrorCode` 를 싣지만 도메인마다 같은 모양의 클래스와 핸들러를 한 쌍씩 둔다. b2b 는 aicc 모듈의 구조(부모 하나 + 핸들러 하나)로 옮기는 중이다. 스켈레톤에도 같은 결함이 있는지 확인한 결과가 설계서 §1 표다.

## 착수 전 결정 (2026-10-26, 사용자)

### 「부모 이름 CodedException」

- 결정: `CodedException`. asp-net-core 형제가 이미 이 이름으로 같은 구조를 갖고 있다.
- 채택하지 않은 대안: `ErrorCodeException`(b2b·aicc 와 같은 이름). 파생 프로젝트로 옮겨 붙일 때 이름 변환이 필요 없다는 장점이 있지만, 사용자는 스켈레톤 사이의 이름 일치를 택했다.

### 「기존 파생 프로젝트 미반영」

- 결정: 반영하지 않는다. 신규 생성 프로젝트만 받는다. 잔여 위험은 사용자가 수용했다.

### 「본문 status 교정 포함」

- 결정: 이번에 함께 고친다.
- 근거: `docs/ERROR_CODES.md` 는 본문 `status` 를 「HTTP 상태 코드」로 정의한다. 지금은 `ErrorResponseModel.status = code.status` 인데 핸들러가 HTTP 상태를 따로 정해 검증 실패가 HTTP 400·본문 404 로 나간다. 근본 원인이 핸들러 중복 문제와 같다(상태를 두 곳에서 정함). 핸들러가 `errorCode.status` 로만 응답하게 바꾸면 enum 값이 곧 HTTP 상태가 되므로, enum 을 교정하지 않으면 HTTP 상태가 바뀐다.
- 채택하지 않은 대안: 본문을 그대로 두는 방식. 핸들러가 계속 HTTP 상태를 따로 정해야 해서 「상태를 정하는 곳은 하나」가 성립하지 않는다.

## 설계 근거

### 「enum 을 HTTP 에 맞추고 HTTP 는 그대로」

- 교정 방향은 둘이다. enum 값을 HTTP 에 맞추면 본문 `status` 만 바뀐다. HTTP 를 enum 에 맞추면 검증 실패가 404 로 나가는 등 실제 상태가 틀려진다. HTTP 상태가 소비자에게 더 넓게 쓰이는 계약이라 HTTP 를 고정했다.
- `IO_ERROR` 는 문서가 400, 핸들러가 500 이었다. I/O 실패는 서버 쪽 문제라 HTTP 500 을 유지하고 문서와 enum 을 500 으로 맞춘다.

### 「EXTERNAL_API_ERROR G014 · SERVICE_UNAVAILABLE_ERROR G016」

- `ApiCallException` 은 임의의 `HttpStatus` 를 받아 본문 코드(G999 500)와 어긋났다. 상태를 `ErrorCode` 로 받게 하면 임의 상태를 받을 수 없으므로, 쓰이는 두 상태(502 기본, 503 연결 실패)만 코드로 둔다.
- G014 는 asp-net-core `ExternalApiError` 와 같은 이름·구분 코드다. Kotlin 에 G013·G015 가 비어 있지만 asp 에서 다른 의미(충돌·인증)로 쓰이므로 피하고 G016 을 쓴다.
- `GATEWAY_TIMEOUT` 을 쓰던 곳은 단위 테스트 1건뿐이라 504 코드는 두지 않는다.

### 「INSERT/UPDATE/DELETE_ERROR 삭제」

- status 200 인 오류 코드다. 사용처는 0건이다. 단일 핸들러는 `errorCode.status` 로 응답하므로, 파생 프로젝트가 `throw CodedException(ErrorCode.INSERT_ERROR)` 를 쓰면 HTTP 200 오류가 나간다. 남길 이유가 없다.

### 「CodedException 을 abstract 가 아니라 open 으로」

- asp-net-core 는 `abstract` 다. Kotlin 은 b2b 가 목표로 하는 「새 코드 = enum 항목 + `throw CodedException(ErrorCode.X)` 한 줄」을 위해 직접 생성을 허용한다. 전용 예외-핸들러 쌍을 만드는 동기가 사라지는 것이 이 작업의 요점이다.

### 「public·internal 에 details 를 두지 않는다」

- b2b 부모는 `details: Map<String, Any>?` 를 싣지만, 스켈레톤 public·internal 에는 그것을 쓰는 예외가 없다. `ErrorResponseModel` 에 필드를 더하는 것은 응답 모양 변경이라 필요가 생길 때 한다.
- batch 는 이미 `ErrorResponseModel.details: String?` 이 있고 예외 3종이 쓰므로 부모에 `details` 를 둔다.

### 「batch Forbidden·InvalidJobParameter 전용 핸들러 유지」

- 두 예외는 응답 `message` 에 `ex.message` 가 아니라 `errorCode.message` 를 싣는다. 어떤 Job 이 존재하는지, 위조 시도 값이 무엇인지 응답에 드러내지 않기 위해서다(기존 핸들러 주석). 단일 핸들러는 `ex.message` 를 내보내므로 정책이 다르다.
- Spring 은 예외 타입에 가장 가까운 `@ExceptionHandler` 를 고르므로, 부모 핸들러와 전용 핸들러가 공존해도 충돌하지 않는다.
- 채택하지 않은 대안: 두 예외의 message 를 항상 `errorCode.message` 로 고정하고 단일 핸들러로 합치는 방식. 로그에서 거부 사유가 사라진다.

### 「로그 수준 4xx warn · 5xx error」

- 지금은 핸들러마다 제각각이다(`ItemNotFound` 는 스택 포함 error, `AccountLocked` 는 warn). 4xx 는 클라이언트 요청 문제라 스택이 필요 없다. asp-net-core `GlobalExceptionHandler` 도 같은 기준이다.

### 「검출 테스트 위치」

- 본문 `status` 단언은 기존 `ErrorResponseContractIntegrationTest`(「오류 응답 계약」, 장치 B 등록됨)에 둔다. 이 테스트가 외부 계약을 고정하는 자리다.
- batch 는 `GlobalExceptionHandler` 테스트가 없었다. Spring Context 없이 standalone MockMvc 로 핸들러 선택(부모 vs 전용)까지 검증할 수 있어 unit 소스셋에 둔다.
